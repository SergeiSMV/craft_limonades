# P0-04 · Аутентификация по бейджу (JWT + argon2)

**Статус:** ✅ завершена (проверено локально и в стеке)
**Задача:** Auth по бейджу (16 цифр → 8/8), argon2, middleware, rate limiting, роли employee/admin (JWT несёт роль), сидинг админа с ролью admin.
**Критерий готовности:** скан бейджа → `/auth/login` выдаёт пару токенов; защищённый роут без валидного токена → 401, с валидным → пускает и знает `user_id`; refresh обновляет access без повторного скана; в пустой базе есть засеянный админ.

Общая архитектура — в [architecture.md](architecture.md). Схема БД (`users`, роли) — в [p0-03.md](p0-03.md).

### Ключевые решения

- **Деление бейджа — на сервере.** Клиент шлёт `{"badge":"<16 цифр>"}`; сервер режет `login=badge[:8]`, `secret=badge[8:]`. В UX/API нет «логин/пароль» — только бейдж.
- **argon2id** (обёртка `alexedwards/argon2id`, PHC-формат) — секрет хранится только хешем.
- **JWT stateless.** access `{sub, role, typ:access, jti, exp}` — короткий (12 ч), проверяется middleware без БД. refresh (30 дней) — только `sub`; роль перечитывается из БД на каждом `/auth/refresh`.
- **Отзыв прав.** Блокировка (`is_active=false`) и смена роли подхватываются на refresh (в пределах TTL access ≤ 12 ч). Отдельного хранилища refresh-токенов нет (по решению — stateless).
- **Rate limiting** (`go-chi/httprate`) на `/auth/login` и `/auth/refresh` — **10/мин по реальному IP клиента** (`X-Real-IP` от nginx, не `RemoteAddr`, иначе за прокси все делили бы один лимит).
- **Роли.** access несёт `role`; `RequireRole("admin")` готов для будущих admin-only ручек (управление пользователями).
- **Сид-админа** — отдельная команда `cmd/seed` (а не hot-path старта), `ON CONFLICT DO NOTHING` (идемпотентно).
- **JWT_SECRET** — из env; если пуст, генерируется эфемерный (токены не переживут рестарт) + warn. В проде обязателен.

## Запуск и проверка критериев готовности

Требуется поднятый стек и применённая схема:
```bash
make up
make migrate-up
make seed          # создаёт админа из .env (ADMIN_BADGE); login = первые 8 цифр
```

После проверки остановить стек достаточно командой `make down` (все контейнеры гасятся,
данные БД сохраняются в volume). Полностью погасить Docker-демон — `colima stop`.

### 1. Login → пара токенов

```bash
curl -s -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' -d '{"badge":"1000000012345678"}'
```
Ожидаемо: `200` + `{"access":"...","refresh":"..."}`. В access-claim — `role`, `sub`=user_id.

### 2. Защищённый роут: без токена 401, с токеном 200 + знает user_id

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/auth/me            # 401
curl -s -H "Authorization: Bearer <ACCESS>" http://localhost:8080/auth/me         # 200 + профиль
```
Ожидаемо: `{"user_id":"…","login":"10000000","full_name":"…","role":"admin"}`.

### 3. Refresh → новый access без скана

```bash
curl -s -X POST http://localhost:8080/auth/refresh \
  -H 'Content-Type: application/json' -d '{"refresh":"<REFRESH>"}'
```
Ожидаемо: `200` + новый `access` (валиден на `/auth/me`).

### 4. Негативные сценарии

```bash
# неверный секрет / несуществующий логин → 401
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' -d '{"badge":"1000000099999999"}'   # 401
# кривой бейдж (не 16 цифр) → 400
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' -d '{"badge":"123"}'                # 400
```

### 5. Rate limiting

```bash
for i in $(seq 1 13); do
  curl -s -o /dev/null -w "%{http_code} " -X POST http://localhost:8080/auth/login \
    -H 'Content-Type: application/json' -d '{"badge":"1000000099999999"}'
done; echo
```
Ожидаемо: первые ~10 → `401`, дальше `429` (лимит 10/мин по IP).

### 6. Засеянный админ

```bash
docker exec infra-db-1 psql -U wms -d craft_wms -c "SELECT login, role, is_active FROM users;"
```
Ожидаемо: строка `10000000 | admin | t`.
