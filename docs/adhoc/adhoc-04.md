# ADHOC-04 · Релизная сборка без разрешения INTERNET

**Статус:** готово; исправлено и проверено на живом DT50S.
**Область:** `adhoc-fe` (Flutter, Android-манифест).
**Найдено:** при проверке P2-01 на устройстве.

## Задача

Релизная сборка приложения не могла обращаться к серверу: любой запрос падал мгновенно,
а пользователь видел «нет связи с сервером» при полностью исправной сети.

## Почему это так долго не замечали

Симптом уводит в сторону. Ошибка приходит от резолвера за 15 мс:

```
The connection errored: Failed host lookup: 'craft.skogi.ru'
```

Выглядит как проблема сети или DNS, и я потратил на эту версию несколько подходов: проверял
маршрут, петлю NAT на роутере, стабильность Wi-Fi. Всё было исправно. Решающим оказалось
расхождение: `curl` с того же устройства в те же минуты давал десять успешных запросов из десяти,
а приложению — отказ. У шелла разрешение есть, у приложения не было.

Вторая причина, по которой это не всплывало раньше: **отладочная сборка работает.** Шаблон Flutter
объявляет `android.permission.INTERNET` в debug- и profile-манифестах, потому что оно нужно
инструментам hot reload. В основной манифест разрешение должен добавить автор проекта, и в релиз
попадает только оттуда. Всё, что проверялось через `flutter run`, работало и скрывало дефект.

Проверка сборок это подтверждает:

```
app-release.apk  →  INTERNET отсутствует
app-debug.apk    →  uses-permission: android.permission.INTERNET
```

`git log -S "android.permission.INTERNET"` по основному манифесту пуст: разрешения не было ни разу
за всю историю репозитория.

## Что сделано

В `android/app/src/main/AndroidManifest.xml` добавлено объявление `android.permission.INTERNET`
с комментарием, объясняющим, почему шаблонного debug-манифеста недостаточно.

Правка на одну строку; кода она не касается.

## Проверка

```bash
cd apps/craft_wms
flutter build apk --release -t lib/main.dart --dart-define-from-file=.env
aapt2 dump permissions build/app/outputs/flutter-apk/app-release.apk
```

Ожидаемо: `uses-permission: name='android.permission.INTERNET'`.

На устройстве после установки: `granted=true`, `GET /api/v1/auth/me` → 200,
вход по скану бейджа → 200.

## Почему дефект дожил до этого дня

На терминалы приложение ставили не сборкой, а `flutter run -t lib/main.dart` — то есть отладочной
сборкой, у которой разрешение приходит из debug-манифеста. Так шли и проходы склада, и тестирование.
Релизная сборка на устройство до сегодняшнего дня попросту не попадала, поэтому дефект и не
проявлялся.

Это выяснилось на прямой проверке: сборка командой из документации, на текущем состоянии
репозитория, разрешения не даёт — а рабочее приложение на терминале его имело.

## Следствие: на складе работала отладочная сборка

Отдельная проблема, которую этот разбор вскрыл. Отладочная сборка на боевом терминале — это:

- **медленно**: Dart исполняется в режиме JIT вместо AOT, интерфейс заметно тяжелее на слабом ТСД;
- **`android:debuggable="true"`**: приложение открыто для отладчика и `run-as`, то есть его
  приватный каталог доступен всякому, кто получит adb к устройству;
- **открытый VM-сервис**: отладочный порт наружу, чего в эксплуатации быть не должно;
- **не то, что проверяли**: релизный путь сборки до сих пор ни разу не проходился целиком,
  а именно в нём и живут отличия — оптимизация, tree-shaking, сжатие кода.

Последний пункт закрыт в тот же день: после исправления вся проверка P2-01 шла на релизной
сборке — вход, проход склада, поиск товара по штрихкоду, работа сканера в обоих режимах.

**До пилота на терминалы должна ставиться релизная сборка.** Команда в документации по деплою
верная, расходилась практика.
