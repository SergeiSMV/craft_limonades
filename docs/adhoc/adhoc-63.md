# ADHOC-63 (fe) · Скорость скана марок в сборке на ТСД

локальная база терминала не менялись.
**Категория:** внеплановая, `adhoc-fe`. Строки в `plan_v3.docx` нет.
**Процесс:** [`picking.md`](../picking.md), поток сборки на ТСД - [`p9/p9-06.md`](../p9/p9-06.md).

## Задача

Маркируемый товар собирается только марками, по скану на бутылку, так что скан марки - самое
частое действие сборки. Каждый скан ждал сеть от 2 до 4 раз подряд:

1. марка в коробе - запрос карточки короба ради адреса ячейки для показа;
2. пик - отправка операции с ожиданием ответа сервера;
3. после пика - заказ с сервера;
4. очередь уменьшилась - заказ с сервера ещё раз.

Сканы подряд при этом обрабатывались одновременно. Второй скан видел заказ без пика первого, и
проверки «марка уже взята» и «больше, чем осталось собрать» могли не сработать. Пик и
перечитывание заказа одновременно читали, меняли и записывали один слепок заказа на терминале,
поэтому последняя запись затирала свой же пик. Тест на пять одновременных пиков с
перечитыванием заказа без исправления оставлял в слепке один пик из пяти.

## Критерий готовности

- Сканы на экране заказа обрабатываются по одному, в порядке прихода.
- Пик марки показывается сразу из слепка терминала, сеть на скан не ждётся.
- Сервер подтверждает пики в фоне, несколько пиков подряд уходят одним запросом.
- Отказ сервера по существу снимает пик с экрана и показывает причину дословно.
- Пики подряд и перечитывание заказа не затирают друг друга в слепке.
- Заказ с сервера перечитывается один раз, когда сканы и отправка стихли.
- «Завершить сборку» сразу после фоновой отправки не отказывает ложным «нужна связь».
- В журнале приложения есть время обработки каждого скана.

## Ключевые решения

### Сканы - строго по одному

`PickingScanActions.onScan` ставит каждый скан в `SerialLock`: следующий скан начинается, когда
предыдущий закончился, и видит заказ уже с его пиком. Скан, открывший выбор варианта или
количество, держит очередь до закрытия окна. Это правильно: окно и есть обработка этого скана.
Ошибка обработки пишется в журнал и следующий скан не останавливает.

### Пик принимается на терминале, сервер подтверждает фоном

`PickingRepositoryImpl.pick` ставит операцию `picking_pick` в очередь, пишет пик в слепок и сразу
возвращает `Right`. Отправку запускает `SyncEngine.drain()` без ожидания. Проход отправляет
очередь пачками, поэтому марки, отсканированные подряд, уходят одним запросом. Сервер
не задваивает пик по `pick_id`, так что бэкенд не менялся.

Если во время прохода позвали `drain()` ещё раз, проход повторяется: пик, поставленный во время
отправки предыдущего, раньше ждал бы таймера повтора или события сети. Временная неудача
повтор не запускает, тогда очередь ждёт таймера, как и раньше. Повторный вызов по-прежнему
возвращается сразу, ничего не отправив, поэтому есть `whenIdle()`, который дожидается конца
идущего прохода. «Завершить сборку» сначала ждёт его, затем сама отправляет очередь.
Иначе завершение сразу после последнего скана видело бы неотправленный пик и отказывало.

### Отказ сервера - из очереди отказов

Отклонённая операция получает статус «отклонена», и «взято» перестаёт её учитывать: пик сходит с
экрана сам. Причину кубит берёт из `OutboxRepository.watchRejected()`: отказ `picking_pick`
этого заказа показывается подсказкой «Сервер отказал: …» дословно. Отказы, которые уже были до
открытия экрана, не показываются. Как и раньше, отклонённая операция остаётся в разделе
очереди для разбора.

### Слепок заказа - запись по одной

Все чтения-изменения-записи слепка (`pick`, `unpick`, `order`, `release`, короба, «не
хватает», `complete`) идут через один `SerialLock` репозитория. `order` читает слепок уже после
ответа сервера и под блокировкой: пик, записанный во время запроса, остаётся своей записью
поверх ответа. Сеть под блокировкой не ждётся, чтобы скан не стоял за чужим запросом. Возврат
пика (`unpick`) по-прежнему ждёт сервер: это редкое действие, и его отказ должен быть виден сразу.

### Заказ с сервера - после паузы

После пика экран перерисовывается из слепка, а заказ с сервера перечитывается один раз, когда
1,5 с (`PickingOrderCubit.reloadPause`) не было ни пиков, ни отправок. Если пик случился во время
перечитывания, ответ не показывается поверх него: экран берёт слепок, где уже лежат и ответ, и
пик.

### Адрес марки - без сети

Адрес ячейки короба, из которого взята марка, нужен только для показа пика.
`ContentsRepository.cachedLoadUnitCell` берёт его из снимка склада терминала со своей очередью
поверх. Сами марки и раньше искались только по данным терминала (`marksByCode`).

### Замер

Каждый скан пишет в журнал приложения (talker, уровень debug) строку «Сборка: скан обработан
за N мс (в очереди сканов M мс)». Подтверждение сервера видно по строке движка «Синхронизация:
отправлено N, отклонено K, осталось R». По времени этих строк считается серия из 20 марок до
экрана и до подтверждения.

## Границы

- Возврат пика, взять/отказаться, короба и «не хватает» по-прежнему ждут сервер - это не
  поток скана.
- Россыпь и товар в коробе без марок по-прежнему спрашивают количество. Само окно не ускорялось,
  но пик после него теперь тоже не ждёт сервер.
- Скан ячейки или короба без подбора по-прежнему запрашивает содержимое с сервера. Это редкий
  случай: обычно источник есть в подборе.
