# ADHOC-42 (ops) · Мониторинг: ошибки в Bugsink, сигналы таймеров, доступность

**Статус:** ✅ завершена (gofmt/build/vet чисты, golangci-lint 0 issues, полный `go test ./...`
зелёный; `bash -n` и `shellcheck -S warning -x` по `deploy/` чисты; Bugsink поднят локально
из prod-compose, событие из бэкенда легло в него с пользователем и полями записи).
**Категория:** внеплановая, `adhoc-ops` (с серверной частью). Строки в `plan_v3.docx` нет.

## Задача

О проблемах сервера узнавали по жалобе кладовщика. Ошибка 500 оставалась строкой в journal;
таймер бэкапа или обновления, который молча перестал запускаться, не видел никто; выключенный
ноутбук или пропавший интернет сообщить о себе не могут.

## Критерий готовности

Ошибки бэкенда (записи журнала уровня error и паники запросов) уходят в свой сервер сбора
ошибок с запросом и пользователем; таймеры update, backup и restore-check сообщают исход
во внешний сервис; доступность снаружи проверяет внешний монитор. Без настроек в `.env.prod`
всё выключено, и стек работает как раньше.

## Ключевые решения

### Три инструмента — три вопроса

- **UptimeRobot** (внешний, бесплатный тариф) — доступен ли сервер снаружи: HTTP-монитор
  `https://craft.skogi.ru/ready` раз в 5 минут. `/ready` отвечает 200, только если бэкенд жив
  и достаёт до базы. Коммерческое использование бесплатного тарифа условиями разрешено.
- **Cronitor** (внешний, бесплатный тариф: 5 мониторов) — отработали ли таймеры: скрипт шлёт
  исход, сервис пишет, если сигнал не пришёл к сроку или пришёл сбой. Скрипты понимают и
  Healthchecks.io — формат сигнала выбирается по адресу; в Healthchecks.io не пришло письмо
  со ссылкой для входа, поэтому основной — Cronitor.
- **Bugsink** (на сервере) — какие ошибки случаются внутри работающего сервера.

Внешние сервисы шлют письма сами; SMTP-ящик нужен только Bugsink.

### Bugsink — свой сервер, совместимый с Sentry

Клиент — штатный `sentry-go`, сервер — Bugsink: один контейнер приложения, данные у себя,
лицензия PolyForm Shield разрешает внутреннее использование. База — свой Postgres в отдельном
контейнере: SQLite в томе Docker Bugsink не рекомендует, а рабочая база, её ночной дамп и
проверка восстановления историю ошибок не задевают. Её не бэкапим.

Интерфейс — на поддомене `errors.craft.skogi.ru` за хостовым nginx с сертификатом Let's
Encrypt: ссылки из писем открываются откуда угодно, и потом туда же сможет отправлять ошибки
портал. Контейнер слушает только loopback. Бэкенд шлёт события по сети compose
(`http://<ключ>@bugsink:8000/<номер>`) — наружу они не выходят. Регистрации нет — входит админ.

Контейнеры Bugsink — в профиле `monitoring`; обёртка `compose()` включает его сама, когда задан
`BUGSINK_SECRET_KEY`. Без него `update.sh` и `install.sh` поднимают стек как раньше.

### Ошибки — из журнала, без правок в каждом обработчике

Свой обработчик slog поверх JSON: запись уровня error и выше пишется в журнал как раньше
и уходит событием — сообщение записи (заголовок), ошибка из атрибута `error` (тип и цепочка),
остальные атрибуты — контекст `log`, пользователь и роль — из контекста запроса. Готовый
`sentry-go/slog` не взял: он шлёт записи «логами Sentry», а Bugsink принимает события ошибок.
Обработчики уже писали 500 через `slog.Error`; вызовы переведены на
`slog.ErrorContext(r.Context(), …)`, чтобы событие знало пользователя, — функциям перевода
ошибок в ответ добавлен параметр запроса.

Middleware даёт запросу свой hub: запрос (заголовок авторизации SDK заменяет на `[Filtered]`)
и тег `request_id` — тот же, что в журнале. Паника уходит событием и пробрасывается дальше:
ответ 500 и запись в журнал по-прежнему делает chi `Recoverer`. Неверный DSN не роняет
сервис — склад важнее уведомлений.

### Сигналы таймеров

`job_ping` шлёт исход по адресу из `JOB_PING_<ИМЯ>`: Cronitor — `?state=complete|fail` с кодом
и текстом, Healthchecks.io — `POST <адрес>/<код выхода>` с текстом. `job_watch` вешает его на
выход скрипта, а `die` запоминает текст ошибки — сигнал «упал» уносит причину. `pg-restore.sh`
уже имеет свой обработчик выхода и шлёт сигнал из него (`job_exit`), только в режиме проверки.
Неудача отправки скрипт не роняет: мониторинг не должен ломать бэкап.

Сигнал `update` (каждые 5 минут) заодно значит «сервер на месте». Перед ним `update.sh`
проверяет `/ready` через хостовый nginx и TLS по имени домена с адресом самого сервера: упавший
nginx или истёкший сертификат дают сбой — это закрывает проверку сертификата, которой нет
в бесплатном UptimeRobot.

## Проверка

```bash
colima start
cd apps/backend
gofmt -l . && go build ./... && go vet ./... && golangci-lint run ./...
DOCKER_HOST="unix://$HOME/.colima/default/docker.sock" TESTCONTAINERS_RYUK_DISABLED=true \
  go test ./... -count=1
cd ../..
for f in deploy/*.sh; do bash -n "$f"; done
docker run --rm -v "$PWD:/mnt" -w /mnt koalaman/shellcheck:stable \
  -S warning -x deploy/*.sh deploy/test_stand/*.sh
colima stop
```

Ожидаемо: всё зелёное. На сервере после включения — в журнале бэкенда при старте
`error reporting enabled`; в Cronitor три монитора зелёные; в UptimeRobot — «Up».
Порядок включения — `docs/deploy/prod-deploy.md`, раздел «Мониторинг».
