## Долг 15 · Пробный ярлык ГЕ помечается на наклейке

Кнопка «Ярлык ГЕ» на экране наладки принтера печатает наклейку с новым идентификатором, но ГЕ
на сервере не заводит. Наклейка физическая и живёт дольше отладки: попав на реальный короб,
она даёт при скане «ГЕ не найдена», и поломку ищут там, где её нет.

Кнопку оставляю — она нужна для наладки принтера. Регистрировать каждую пробную печать на
сервере не стал: справочник засорился бы коробами, которых никто не собирал.

### Критерий готовности

Ярлык, напечатанный с экрана наладки, несёт на себе пометку «ПРОБНАЯ». Ярлык из приёмки
не изменился ни в одном байте.

### Что сделано

| Файл                                          | Правка                                           |
|-----------------------------------------------|--------------------------------------------------|
| `lib/core/printer/load_unit_label.dart`        | необязательная пометка `trialMark`               |
| `lib/core/printer/printer_service.dart`        | `printLoadUnitLabel` принимает пометку           |
| `features/debug/.../printer_probe_page.dart`   | экран наладки печатает с пометкой                |
| `assets/i18n/ru.i18n.json`                     | `printer_probe.trial_mark` — «ПРОБНАЯ»           |
| `test/core/printer/load_unit_label_test.dart`  | эталон рабочего ярлыка и раскладка пометки       |

### Ключевые решения

**Пометка — параметр ярлыка, а не отдельный шаблон.** `LoadUnitLabel` получил необязательный
`trialMark`. Без него (и с пустой строкой) ярлык тот же, что был. Текст пометки передаёт экран
наладки из i18n, сам ярлык о слове «ПРОБНАЯ» не знает.

**Рабочий ярлык закреплён байт в байт.** Строка пометки добавляется после всех команд рабочего
ярлыка, перед `PRINT`. Тест сверяет команды рабочего ярлыка с эталоном, снятым с кода до
правки: ярлыки из приёмки уже клеят на короба, и любой их сдвиг пришлось бы подтверждать печатью.

**Место — зазор между QR и коротким кодом.** На рулоне 58 × 40 мм между низом QR и строкой кода
61 точка; пометка шрифтом «3» (высота 24) встаёт посередине, по ~18 точек воздуха с каждой
стороны. Шрифт тот же, что у кода: проверенная кириллица при `CODEPAGE 1251` и без риска
задеть соседние элементы. Центровка посчитана по ширине символа из спецификации шрифта —
поэтому подтверждена печатью.

**Пометка проходит `sanitizeTsplText` и уходит в CP1251.** Текст из i18n — тоже внешние данные
для команды принтера: кавычка в нём закрыла бы команду `TEXT` раньше времени.

**Удалил неиспользуемую `labelText`.** Функция-заготовка под кириллицу на ярлыке ГЕ нигде
не вызывалась, а её комментарий («на ярлыке нет русского текста») стал неверным.

### Проверка

```
cd apps/craft_wms
dart run build_runner build
flutter analyze
flutter test
flutter build apk --release -t lib/main.dart --dart-define-from-file=.env
```

Ожидаемо: `No issues found!`, `All tests passed!`, собранная APK.

**Проверка на живом устройстве** (DT50S + XP-P323B, рулон заправлен с ограничителем):
меню «⋮» → «Принтер» → «Ярлык ГЕ» — между QR и коротким кодом напечатано «ПРОБНАЯ».

Пройдено: пометка напечатана на наклейке.

### Границы

Короб, удалённый или отброшенный в приёмке до «Завершить», по-прежнему оставляет
напечатанный ярлык без ГЕ на сервере. Это цена печати без связи, а не тот же дефект:
терминал предупреждает о ней в диалогах удаления и отбрасывания.

Раскладка пометки рассчитана на рулон пилота 58 × 40 мм. На заметно более низкой этикетке
зазора под пометку не останется — тест раскладки это поймает.

## Долг 13 · Отмена привязки больше не гоняется с отправкой

Отмена шага в проходе (Undo) снимает из очереди ещё не ушедшую привязку ШК (ADHOC-14).
Снятие читало статус операции, а удаляло её отдельным запросом; движок синхронизации так же
отдельно читал очередь и отдельно ставил `sending`. Окно было в обе стороны:

- движок забрал операцию между чтением и удалением — отмена удаляла строку в полёте и говорила
  «отменено», а привязка уезжала на сервер;
- отмена удалила строку после того, как движок прочитал очередь, — движок всё равно отправлял
  её: `markSending` по удалённой строке молча ничего не делал.

### Критерий готовности

Исход решает тот, кто успел первым: снятая операция не уходит на сервер, а забранная
в отправку не снимается и отмена отвечает «поздно».

### Что сделано

| Файл                                                   | Правка                                       |
|--------------------------------------------------------|----------------------------------------------|
| `lib/core/outbox/outbox_repository.dart`                | `discardIfPending`, `markSending` → `bool`   |
| `lib/features/stock/data/catalog_repository.dart`       | отмена через условное снятие                 |
| `lib/core/sync/sync_engine.dart`                        | отправляется только забранное                |
| `test/core/outbox_repository_test.dart`                 | условное снятие и захват                     |
| `test/features/stock/catalog_repository_cache_test.dart` | снятая отменой операция не отправляется      |

### Ключевые решения

**Проверка и действие — один запрос, а не транзакция с блокировкой.** Снятие стало условным
`DELETE … WHERE operation_id = ? AND status = 'pending'`, захват в отправку — `UPDATE` без
предварительного чтения, возвращающий, нашлась ли строка. Локальная база выполняет запросы по
одному, поэтому два запроса не перемежаются: какой прошёл первым, тот и решил судьбу операции.
Флаг «занята отправкой» или транзакция вокруг чтения и записи дали бы то же, но сложнее.

**Снятая операция для движка — не ошибка.** `sendOne` по уже снятой строке возвращает успех
без обращения к серверу, проход очереди просто пропускает её.

**Чтение очереди в отмене осталось — оно ищет кандидата, но не решает.** Решает условное снятие:
если оно ничего не удалило, отмена отвечает «поздно», и локальный след привязки не откатывается.

### Проверка

```
cd apps/craft_wms
flutter analyze
flutter test
```

Ожидаемо: `No issues found!`, `All tests passed!` (462 теста). Новые тесты на старом коде
падают — проверил, откатив правку: снятая отменой операция уходила на сервер.

Окно гонки — миллисекунды, руками на терминале его не поймать, поэтому проверка на DT50S
не требуется: поведение Undo для человека не изменилось.

### Границы

Отмена ищет операцию среди первых 100 ожидающих (предел чтения очереди). При очереди длиннее
свежая привязка в выборку не попадёт, и отмена ответит «поздно», хотя операция ещё не ушла.
Ошибки в безопасную сторону: ничего лишнего не снимается. На практике очередь такой длины
на одном терминале не набирается.

## Долг 9 · Вход без связи — не позже суток от последнего контакта с сервером

Без сети терминал поднимал сессию по сохранённому профилю, пока жив refresh-токен — 30 дней.
Подпись токена клиент проверить не может, запрос на отзыв без связи не дойдёт: терминал
с отозванным доступом работал до конца срока токена.

Сам офлайн-вход остаётся: без него терминал, перезагруженный вне зоны Wi-Fi, упирается в экран
входа, и весь офлайн-кэш недостижим.

### Критерий готовности

Без связи терминал пускают, только если последний успешный обмен с сервером был не дольше
24 часов назад. Предел одинаков для всех ролей.

### Что сделано

| Файл                                          | Правка                                         |
|-----------------------------------------------|------------------------------------------------|
| `lib/core/auth/token_storage.dart`             | отметка последнего контакта `last_contact`     |
| `lib/core/network/auth_interceptor.dart`       | отметка на успешный ответ с токеном            |
| `lib/core/auth/auth_repository.dart`           | `offlineLoginWindow` = 24 ч, проверка в офлайн-входе |
| `test/core/auth/auth_repository_test.dart`     | окно офлайн-входа, отметка в `me()`            |
| `test/core/network/auth_interceptor_test.dart` | когда контакт отмечается, а когда нет          |

### Ключевые решения

**Контакт — успешный ответ на запрос с токеном.** Отметку ставит `AuthInterceptor` на любой
ответ 2xx, ушедший с заголовком `Authorization`: такой ответ доказывает, что сервер принял
именно эту сессию. Вход и пробы без токена контактом не считаются, отказ сервера — тоже.
Повтор запроса после обновления access идёт мимо `onResponse`, и контакт отмечается там отдельно.

**Пишется не чаще раза в минуту.** Предел — сутки, а запись в зашифрованное хранилище на каждый
запрос прохода — лишняя работа. Отметка лежит рядом с токенами в `flutter_secure_storage`.

**`me()` пишет отметку сам.** Выход стирает отметку вместе с токенами. Вход сразу после выхода
попал бы в минутную паузу интерсептора и остался бы без отметки — то есть без офлайн-входа.

**Отметки нет — без связи не пускаю.** Так ведёт себя терминал, обновлённый с версии без
отметки: первый вход со связью её заводит. Пускать по одному сроку токена значило бы оставить
лазейку, ради закрытия которой задача и делалась.

**Окно — сутки (решение заказчика).** Отозванный доступ гаснет на терминале не позже чем через
24 часа, а смена, начатая в мёртвой зоне после вчерашней работы, не встаёт.

### Проверка

```
cd apps/craft_wms
flutter analyze
flutter test
flutter build apk --release -t lib/main.dart --dart-define-from-file=.env
```

Ожидаемо: `No issues found!`, `All tests passed!` (472 теста), собранная APK.

**Проверка на живом DT50S** (релизная сборка):

1. Со связью войти — заводится отметка контакта.
2. Выключить Wi-Fi, закрыть приложение из «Недавних», запустить — вход без бейджа.
3. Без Wi-Fi перевести дату терминала на +25 часов (отключив «Время сети»), закрыть
   и запустить приложение — экран входа.
4. Вернуть «Время сети» и Wi-Fi, войти бейджем.

Пройдено: на шаге 2 терминал вошёл без бейджа, на шаге 3 показал экран входа.

### Границы

Время берётся с часов терминала, и перевод их назад продлевает окно. Это принятый риск:
защититься от него без сервера нельзя, а для кладовщика это не случайное действие.

Отзыв доступа на сервере по-прежнему действует при первом же выходе терминала на связь:
протухший или отозванный refresh — ответ сервера, а не отсутствие связи, и в приложение
по нему не пускают.
