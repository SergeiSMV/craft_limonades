# ADHOC-27 (ops) · Тестовый стенд на снимке боевой базы

**Статус:** ✅ завершена (shellcheck и `bash -n` чисты; стенд проверен вживую: снимок с прода,
развёртывание, миграции ветки, портал, `reset` к чистому снимку).
**Категория:** внеплановая, `adhoc-ops`. Строки в `plan_v3.docx` нет.

## Задача

Проверять новые миграции, бэкенд и портал на настоящих данных до мержа, а не на проде. Нужен
локальный стенд, максимально близкий к боевому: база — снимок прода, свежий по команде или
прежний; поверх — миграции и код текущей ветки.

## Критерий готовности

Одной командой стенд поднимается на снимке боевой базы с миграциями текущей ветки; снимок
обновляется по команде; база возвращается к снимку без похода на сервер; стенд не задевает
dev-стек и не имеет доступа к боевой базе.

## Ключевые решения

### Снимок, а не репликация

Живая репликация с прода стенду не подходит: реплика только читает, а первая же новая
миграция ветки разводит схемы и останавливает поток. Поэтому стенд работает на снимке:
`stand.sh pull` снимает свежий, `up` поднимает на последнем или на базе после прошлых тестов,
`reset` возвращает базу к снимку, `refresh` — свежий снимок и стенд на нём.

### Снимок снимается внутри боевого контейнера

`pull` уходит на сервер по SSH и запускает `pg_dump -Fc` внутри контейнера БД боевого
compose-проекта. Имя базы и пользователя берутся из окружения самого контейнера, поэтому
`.env.prod` (он у root) читать не нужно и sudo не требуется — пользователю достаточно группы
`docker`. Дамп пишется во временный файл и становится снимком только после проверки сигнатуры
`PGDMP`: оборванный обмен не подменяет последний снимок. Снимки — с правами 600, хранится
пять последних.

### Миграции ветки — тем же бинарём, что на проде

База стенда разворачивается из снимка (`pg_restore --no-owner --no-privileges
--exit-on-error`), затем бэкенд собирается из рабочего дерева ветки, и миграции накатывает
бинарь `migrate` из этого образа — как `update.sh` на проде. Недовосстановленная база
останавливает стенд: тест на ней врал бы.

### База стенда помечена снимком

Удачное восстановление последним шагом пишет в комментарий базы имя снимка, и `up` считает
базу развёрнутой только по этой метке, а не по наличию тома. Прерванное восстановление
оставляло том без данных; следующий `up` принимал его за базу и накатывал миграции на пустую
схему — стенд поднимался без пользователей, и вход не проходил. Теперь такой том
разворачивается из снимка заново с предупреждением. Перед восстановлением скрипт ждёт базу
по TCP: при первом старте тома образ postgres поднимает временный сервер инициализации только
на сокете и гасит его, и подключение в это окно обрывалось бы. `status` показывает, из какого
снимка развёрнута база.

### Отдельный compose-проект

Стенд — проект `craft-stand` со своим томом и своими портами (база — `127.0.0.1:5433`, портал
и API — `8090` на всех интерфейсах, чтобы до него доходил ТСД). Обычный dev-стек на 5432/8080
живёт рядом. Подключения к боевой базе у стенда нет: `DATABASE_URL` смотрит только на свой
контейнер. Секрет JWT — свой, создаётся при первом запуске: токены прода стенд не принимает.

### Раскладка как у боевого vhost

nginx стенда отдаёт портал на `/` с возвратом `index.html` для любых путей, API — под
`/api/`, пробы — на корне. Портал собирается с относительным `BASE_URL=/api/v1/`, как боевой
бандл, поэтому работает на одном origin без CORS.

### `destroy` убирает всё, что создал стенд

Контейнеры, базу, образ бэкенда и снимки — с подтверждением. Снимки удаляются тоже: в них ФИО,
логины и хеши паролей, лежать без нужды им незачем, а новый снимается за секунды. Оставить их
можно ключом `--keep-snapshots` — чтобы воспроизвести падение миграции на тех же данных или
поднять стенд вне LAN, где свежий снимок не снять. Остановка с сохранением базы — `down`.

### ТСД — через APK стенда и пустую очередь

`stand.sh apk` собирает релизную APK с адресом машины в LAN, но не ставит её: у APK стенда тот
же идентификатор приложения, что у боевой, и очередь операций переживает переустановку.
Неотправленная операция стенда после возврата боевой APK ушла бы на прод. Переключать терминал
можно только с пустой очередью или через удаление приложения — это записано в инструкции.

## Команды проверки критериев готовности

```
colima start
docker run --rm -v "$PWD:/mnt" -w /mnt koalaman/shellcheck:v0.10.0 -S warning -x deploy/*.sh deploy/test_stand/*.sh
bash deploy/test_stand/stand.sh refresh
bash deploy/test_stand/stand.sh psql -At -c 'select version, dirty from schema_migrations'
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8090/ready
bash deploy/test_stand/stand.sh portal
curl -s http://localhost:8090/ | grep -o '<title>[^<]*</title>'
bash deploy/test_stand/stand.sh destroy --yes
colima stop
```

Ожидаемо: shellcheck без вывода; `migrate up: ok`, три контейнера `healthy`; версия схемы —
последняя миграция ветки, `f`; `/ready` — `200`; заголовок портала «КЛ: Склад - портал»;
после `destroy` нет ни контейнеров, ни тома, ни образа `craft-stand-backend`, ни снимков.

Проверил вживую: снимок с прода — 256 КБ; на нём миграция `000022` (P6-01) прошла поверх
боевых данных (780 товаров, 648 ячеек, 280 строк остатка, 7 коробов), схема 22; запись,
добавленная в базу стенда, после `reset` исчезла, схема снова 22; портал отдаётся на корне
и на глубоких путях. `destroy`: отказ в подтверждении ничего не трогает, `--keep-snapshots`
удаляет контейнеры, том и образ и оставляет снимок, без ключа удаляется и снимок.

## Границы задачи

Стенд не повторяет TLS и домен, таймеры обновления и бэкапа, образ из GHCR. Отдельного
идентификатора приложения для ТСД стенда нет: переключение терминала — через пустую очередь.
