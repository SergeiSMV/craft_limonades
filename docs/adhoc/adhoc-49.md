# ADHOC-49 (be) · Должности с настраиваемыми правами вместо ролей

**Статус:** ✅ завершена (gofmt/vet чисты, golangci-lint 0 issues, весь бэкенд с Docker зелёный;
миграция 33 прогнана на стенде поверх снимка боевой базы, на копии — вверх, вниз и снова вверх).
**Категория:** внеплановая, `adhoc-be`. Строки в `plan_v3.docx` нет.

## Задача

Ролей было две: `employee` — кладовщик на ТСД, `admin` — всё остальное. Состав людей и
полномочий на складе шире: старший смены заводит пересчёт, оператор офиса решает только
проблемы склада, кто-то грузит справочники. Нужны должности с набором прав, а функции должны
проверять право, а не роль. Заодно — первое управление пользователями: до этой задачи
пользователей заводили сидером и руками в базе.

Это серверная часть. Экраны «Пользователи» и «Должности» в портале и вкладки по правам —
ADHOC-50; ТСД на правах вместо роли — ADHOC-51. В `main` три задачи уходят вместе.

## Критерий готовности

- У пользователя — должность, у должности — права из фиксированного списка.
- Каждая ручка, которая раньше требовала `admin`, требует своё право; ручки ТСД — право «работа
  на ТСД».
- Смена должности, прав и блокировка действуют сразу, без нового токена.
- API: права, должности (список, завести, изменить, удалить пустую), пользователи (список,
  завести по бейджу или по логину с паролем, изменить, заблокировать, выдать новый бейдж или
  пароль).
- Систему нельзя оставить без управления.
- Нынешние пользователи переезжают без изменения доступа.

## API

- `GET /api/v1/rights` → `{"rights": ["tsd", …]}` — коды в порядке показа.
- `GET /api/v1/positions` → `[{id, name, rights, is_system, users}]` — системная первой.
- `POST /api/v1/positions {name, rights}` → `201 {id}`; `PATCH /positions/{id}` → `204`;
  `DELETE /positions/{id}` → `204`, на должности есть люди — `409`.
- `GET /api/v1/users` → `[{id, full_name, position_id, position_name, login?, username?,
  is_active, created_at}]` — у бейджа виден логин (первые 8 цифр), секрет — никогда.
- `POST /api/v1/users {full_name, position_id, badge | username + password}` → `201 {id}`.
- `PATCH /api/v1/users/{id} {full_name?, position_id?, is_active?, badge? | password?}` → `204`.
- `GET /api/v1/auth/me` — добавлены `position` и `rights`; `role` остался для старых сборок.

Ошибки — `400` (ввод), `404` (нет должности или пользователя), `409` с текстом для экрана:
название или бейдж заняты, системная должность, должность с людьми, последний администратор,
блокировка себя.

## Ключевые решения

- **Права читаются из базы на каждый запрос**, а не из токена: иначе новое право или блокировка
  действовали бы только с выпуском нового access-токена. Один запрос по индексу — на нынешнем
  потоке незаметно.
- **Системная должность «Администратор» — все права, в том числе будущие**, её нельзя изменить и
  удалить. Список прав в строке системной должности код не читает.
- **Систему нельзя оставить без управления.** Каждая правка пользователя или должности идёт в
  транзакции под одной рекомендательной блокировкой; после неё проверяется, что остался хотя бы
  один активный пользователь с правом «пользователи», иначе — откат с понятным текстом. Себя
  заблокировать нельзя.
- **Вход у пользователя один** — бейдж или логин с паролем (ограничение схемы с P1-01-1).
  Кому нужны и ТСД по бейджу, и портал по паролю — две учётки. Новый бейдж выдаётся взамен
  прежнего, новый пароль — взамен прежнего; поменять вид входа нельзя.
- **Пароль — от 8 символов**, логин — 3–64 без пробелов, бейдж — ровно 16 цифр, как при входе.
- **Роль осталась производной**: `admin` — у кого право «пользователи». Её читают сборки ТСД и
  портала до ADHOC-50/51 и метка события Bugsink.
- **Миграция переносит роли один к одному**: `admin` → «Администратор», `employee` →
  «Кладовщик» (право `tsd`). У стартовых должностей постоянные id; «Кладовщик» — значение по
  умолчанию `users.position_id`, поэтому прежние вставки без должности (сидер, тесты) работают.
- **Журнал** — `audit_log`: `position.create|update|delete`, `user.create|update`; секреты не
  пишутся — только «бейдж сменён», «пароль сменён».
