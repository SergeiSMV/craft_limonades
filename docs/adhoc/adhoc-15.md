# ADHOC-15 (ops) · Порядок миграций при обновлении и проверка шаблонных значений

**Статус:** ✅ готово (`bash -n` чист, `shellcheck -S warning -x` 0 issues, проверки systemd-юнитов
проходят; новая логика проверки настроек прогнана на пяти случаях).
**Категория:** внеплановая, `adhoc-ops`. Строки в `plan_v3.docx` нет.

## Задача

Разбирал вопрос «применена ли на проде миграция `000008`» и нашёл два дефекта в скриптах деплоя.
Сама миграция оказалась применена (схема версии 8, без `dirty`) — но выяснить это можно было
только вручную, и по дороге вскрылось, что проверка готовности сервера врёт.

### 1. Миграции применялись после подъёма нового контейнера

В `update.sh` шаги шли в порядке `compose pull` → `compose up -d` → `migrate up`. То же и в
`install.sh`: `up -d` → ожидание healthcheck → `migrate up` → `seed`. Скрипт работает
под `set -euo pipefail`, поэтому упавшая миграция роняла обновление — но роняла **после** того,
как `up -d` уже пересоздал контейнер с новым образом. Итог: новый код работает против старой
схемы, а снять его некому, потому что скрипт к этому моменту мёртв.

Снаружи такой сервер выглядит здоровым. Проба `/ready` делает один `Ping` пула соединений и про
версию схемы не знает ничего, так что отвечает 200 и при разъехавшейся схеме. Дополняет картину
то, что `golang-migrate` помечает сорванную миграцию флагом `dirty`: каждый следующий тик таймера
обновления (раз в 5 минут) падает на ней же и так же молча — единственный след остаётся в journal,
куда никто не смотрит.

### 2. Проверка шаблонных значений считала собственный комментарий

Пункт «Что готово, а что ещё нужно» в панели `craft.sh` искал незаполненные значения так:

```
tpl="$(grep -cE '(CHANGE_ME|example\.ru)' "$ENV_FILE" 2>/dev/null || echo 0)"
```

Грепом по **всему файлу**, включая комментарии. Шаблон `infra/.env.prod.example` несёт в шапке
строку «Значения ниже с CHANGE_ME / example — заменить на свои», которая переезжает в `.env.prod`
при копировании и содержит оба маркера. Она и считалась незаполненной переменной: на исправном
сервере чек-лист показывал «в настройках осталось 1 шаблонных значений».

Вред не в ложной тревоге, а в том, что после неё на проверку нельзя опереться. Счётчик не говорит,
какая переменная не заполнена, поэтому настоящее шаблонное значение утонуло бы в той же единице —
а разница между забытым доменом и забытым `ADMIN_PASSWORD` велика: второе означает вход в портал
с правами администратора по значению из публичного шаблона.

Побочно: `grep -c` при нуле совпадений печатает `0` **и** выходит с кодом 1, поэтому `|| echo 0`
дописывал второй ноль и в переменную попадало двустрочное значение. Сегодня это давало верный
итог случайно — арифметика на такой строке не проходит, условие ложно, галочка зелёная.

## Критерий готовности

Упавшая миграция не пускает новый код к старой схеме. Проверка настроек не срабатывает на
комментариях и называет незаполненные переменные по имени.

## Что сделано

| Файл                | Правка                                                                      |
|---------------------|-----------------------------------------------------------------------------|
| `deploy/update.sh`  | `migrate up` перенесён перед `compose up -d`; расчёт `after` оставлен после   |
| `deploy/install.sh` | тот же порядок: `pull` → `migrate up` → `up -d` → ожидание healthcheck → сид |
| `deploy/craft.sh`   | проверка шаблонных значений: только строки-присваивания, вывод имён           |

## Ключевые решения

### Миграции — до подъёма контейнера, но после `pull`

Порядок стал `pull` → `migrate up` → `up -d`. Неудачная миграция теперь роняет обновление **до**
смены кода: работает прежний контейнер против прежней схемы, и они друг другу соответствуют.

Образ для миграции берётся уже свежий — `pull` прошёл выше, значит накатываются миграции новой
версии, а не старой. Отдельно поднимать БД не понадобилось: `compose run` тянет зависимости
сервиса, а у `backend` прописан `depends_on: db` с `condition: service_healthy`.

Расчёт `after` (сравнение образа до и после, чтобы сказать «обновление применено») **остался
после `up -d`** и переносу не подлежит: `compose images` отдаёт образ созданного контейнера,
а не скачанный `pull`'ом. До пересоздания там лежит прежний id, и обновление всегда выглядело
бы как «новых обновлений нет».

В `install.sh` порядок выровнен по тому же правилу. Пункт панели называется «Установить /
переустановить», то есть скрипт гоняется и поверх работающего сервера с живой базой — там
дефект ровно тот же, что в обновлении. Сид остался **после** ожидания healthcheck: схема
к этому моменту накачена, а живой контейнер подтверждает, что образ рабочий, и заведение
админа не упрётся в битый бинарь.

### Проверка настроек называет переменные, а не считает их

Вместо счётчика проверка отдаёт список имён. Комментарии отсекаются до поиска
(`grep -vE '^[[:space:]]*#'`), затем берутся только строки вида `ИМЯ=…` с маркером в значении.
Печатаются **имена**, значения не выводятся — секреты в чек-лист не попадают.

Отказ от `grep -c` заодно убрал историю с `|| echo 0`: считать больше нечего, проверяется
непустота списка.

### Что решил не делать

Не стал выводить версию схемы наружу — ни отдельным эндпоинтом, ни полем в `/ready`. Мысль была
в том, чтобы состояние схемы читалось без SSH, но панель `craft.sh` отвечает на этот вопрос
за несколько секунд, и расширять ради того же ответа контракт пробы незачем. Проба отвечает
на вопрос «принимать ли трафик», а не «какая версия схемы».

## Команды проверки критериев готовности

Синтаксис и статический анализ скриптов — тот же набор, что гоняет гейт `ci-deploy`:

```
for f in deploy/*.sh; do bash -n "$f"; done
shellcheck -S warning -x deploy/*.sh
```

Ожидаемо: обе команды молчат и выходят с кодом 0.

Логика проверки настроек прогнана на пяти случаях (нетронутый шаблон; заполненный файл с
комментарием из шаблона; заполненный, кроме `ADMIN_PASSWORD`; закомментированные присваивания;
имя с ведущим отступом). Ожидаемо: на нетронутом шаблоне — пять имён через пробел
(`DEPLOY_DOMAIN CERTBOT_EMAIL POSTGRES_PASSWORD JWT_SECRET ADMIN_PASSWORD`), на заполненном файле
и на закомментированных присваиваниях — пусто, на забытом пароле — ровно `ADMIN_PASSWORD`.

Проверка на боевом сервере — пункт 5 панели («Что готово, а что ещё нужно»):

```
sudo bash deploy/craft.sh
```

Ожидаемо: строка «шаблонных значений не осталось» и «схема БД: версия 8». Выход из панели —
пункт 0.

## Границы задачи

Правятся только скрипты деплоя: Go-код, схема БД и приложение не затронуты, миграций задача
не добавляет.

Проверить порядок шагов на боевом сервере вживую не мог: правка едет туда авто-обновлением
после мержа в `main`, и увидеть новый порядок можно будет в journal следующего прогона
(`Миграции…` раньше строки `Применяю (up -d …)`).
