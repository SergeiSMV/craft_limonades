# ADHOC-08 (fe) · Единая точка раздачи сканов вместо подписки в каждом экране

**Статус:** ✅ готово (analyze 0, 236 тестов зелёные, релизная APK собрана).
Осталось сделать: проверка сканером на DT50S в intent-режиме — поведение подписчиков не менялось,
но раздача теперь идёт другим путём.
**Категория:** внеплановая, `adhoc-fe`. Строки в `plan_v3.docx` нет.

## Задача

Предыдущая задача починила два места, где скан не доходил до получателя, — но не механизм,
из-за которого это стало возможным.

Механизм был такой: каждый экран подписывался на поток кодов сам и сам решал, его ли это код.
Правило «мой ли скан» жило в каждом подписчике отдельно, подписок на один поток было семь,
а случая **«код не взял никто»** не существовало вовсе — скан просто исчезал, не оставляя даже
записи в логе. Именно так и потерялись коды в диалоге привязки ШК: экран под диалогом перестаёт
быть верхним, диалог подписан не был, и код ушёл в тишину. Единственным сигналом оказалась
жалоба на пустое поле.

Пока «никто не взял» не является событием, следующее упущение такого рода снова обнаружится
только на устройстве.

## Критерий готовности

Одна подписка на поток вместо семи. Код достаётся одному получателю — верхнему в стопке.
Скан, который никто не взял, попадает в лог. Поведение подписчиков не меняется.

## Ключевые решения

### Роутер раздаёт, миксин остаётся точкой подключения

`ScanRouter` держит единственную подписку и раздаёт коды зарегистрированным получателям;
`HardwareScanListener` переписан поверх него. У семи существующих подписчиков не изменилась ни
одна строка: они по-прежнему подмешивают миксин и реализуют `onHardwareScan`. Менять их API
ради внутренней перестройки было бы напрасной правкой семи файлов.

### «Взял первый подходящий» вместо «получают все текущие»

Раньше код доставлялся **каждому** подписчику, который считал себя верхним, — то есть при двух
одновременно текущих получателях один скан обработался бы дважды. Такого сочетания в приложении
сегодня нет, но и запрета на него не было. Теперь код предлагается с конца стопки и уходит
первому, кто его взял; получатель может и отказаться — тогда код идёт дальше.

### Порядок стопки — порядок регистрации

Получатели складываются в порядке монтирования, а он для маршрутов совпадает с порядком
навигации: диалог монтируется после экрана, значит окажется последним и получит код первым.
Проверка «я верхний в стопке» (`ModalRoute.isCurrent`) при этом сохранена — без неё экран
остался бы получателем и под открытой поверх него карточкой товара.

### Отсечения дублей в роутере нет

Тут я поправил себя по ходу работы: сначала счёл шесть отдельных `ScanDeduper` дублированием
и собирался свести их в один. Проверка вызовов показала обратное — каждый сводит **два входа
своего получателя**: Enter из поля ввода (клавиатурный режим) и поток интентов. Поле роутеру
не видно, поэтому источники может сводить только сам получатель. Один скан даёт в потоке ровно
одно событие, и дублировать там нечего. Дедуперы остались на местах.

### Скан, который никто не взял, пишется в лог

Ветка, которой раньше не было. Такой скан означает либо забытую подписку — так и терялись коды
в диалогах, — либо осознанное «здесь сканы не нужны», как в листе выбора товара. И то, и другое
теперь видно на диагностическом экране логов, а не только по жалобе кладовщика.

**Автоматической вставки в сфокусированное поле не делал.** Идея заманчива: тогда любое поле
ввода работало бы в обоих режимах сканера без единой строки кода, включая ненаписанные экраны.
Отвергнута по двум причинам. Через текстовое поле проходит только строка, а символика теряется —
на ней держится развилка «QR → грузовая единица», где основным источником выбран AIM. И вставка
работала бы там, где сканы намеренно не нужны: лист выбора товара открывается с автофокусом
на поиске, и случайный код попадал бы прямо в него.

### Подписка на поток поднимается при первом получателе

И закрывается, когда ушёл последний. Держать открытым платформенный поток без подписчиков
незачем — на экране входа до опроса устройства получателей нет вовсе.

## Что сделано

- **`core/scanner/scan_router.dart`** — новый: одна подписка, стопка получателей, раздача
  с конца, лог невзятого скана, счётчик получателей для диагностики.
- **`core/scanner/hardware_scan_listener.dart`** — переписан поверх роутера: регистрация вместо
  своей подписки, `canAcceptScan` вместо внутренней проверки маршрута.
- **`test/support/fake_scanner_service.dart`** — роутер поднимается вместе с фальшивым
  сканером, поэтому существующие тесты не знают об устройстве раздачи.

Экраны, диалоги и листы не правились. Правок бэкенда, миграций и изменений API нет.

## Проверка

```
cd apps/craft_wms
flutter analyze          # 0 issues
flutter test             # 236 тестов
flutter build apk --release -t lib/main.dart --dart-define-from-file=.env
```

Тестами закрыты: код достаётся верхнему получателю, а не всем сразу; после закрытия верхнего
код возвращается нижнему; неготовый получатель пропускается; отказавшийся передаёт код дальше;
**невзятый скан попадает в лог**; без получателей поток не слушается; получатель, открывающий
диалог прямо в обработчике, не ломает раздачу.

Все ранее написанные тесты сканирования — экран входа, «Остатки», выбор и работа с ячейкой,
диалог привязки, лист смены ячейки — остались без правок и проходят через новый механизм.
Это и есть проверка того, что поведение подписчиков не изменилось.

## Границы задачи

- **Проверка на DT50S не выполнена.** Поведение подписчиков не менялось, но путь доставки
  теперь другой, и живой intent-режим этой правкой не проверялся.
- **Автовставка в сфокусированное поле не делалась** — см. решения выше.
- **Лист выбора товара по-прежнему без сканов** (решение предыдущей задачи). Разница в том,
  что теперь такой скан виден в логе, а не исчезает.
- **Правило «поток — только верхнему в стопке» сохранено.** Задача меняет место, где оно
  живёт, и добавляет ветку «никто не взял», а не переписывает саму адресацию.
