# ADR-0006 · Двухтокенный JWT (access/refresh) + secure storage

**Статус:** Принято

## Контекст
Кладовщик не должен пересканировать бейдж посреди операции, когда протух токен. На складе бывает
офлайн. Токены нельзя хранить на устройстве в открытом виде.

## Решение
Два JWT: **access** (короткий, дефолт 12 ч) прикладывается к каждому запросу; **refresh** (длинный,
30 дней) молча продлевает сессию. Тип токена в claim `typ` — refresh нельзя использовать как access.
Подпись HS256; на разборе принимаем только HMAC (защита от подмены алгоритма).

Клиент: **JWT-интерсептор** dio на 401 сам дёргает `/auth/refresh` (отдельным «голым» dio, без
рекурсии), сохраняет новый access и повторяет запрос один раз. Токены — в **flutter_secure_storage**
(Android Keystore); при старте `AuthCubit.restore()` тихо восстанавливает сессию. Refresh протух →
хранилище чистится → экран входа. На refresh бэкенд перечитывает пользователя из БД — блокировка и
смена роли подхватываются.

## Последствия
- **+** Бесшовная работа: протухший access обновляется незаметно; сессия переживает перезапуск.
- **+** Секьюрное хранение; блокировка/роль применяются на ближайшем refresh.
- **−** Долгий refresh (30 д) — компромисс ради офлайна; отзыв — через `is_active` (проверяется на refresh).
