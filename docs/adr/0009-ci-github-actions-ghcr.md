# ADR-0009 · CI на GitHub Actions + образы в GHCR

**Статус:** Принято

## Контекст
Монорепо с двумя стеками: легко сломать одну часть, правя другую. Нужен автоматический контроль
(линт, тесты, сборка) до мержа и воспроизводимые образы для деплоя. Разработчик один.

## Решение
**GitHub Actions**, один workflow `.github/workflows/ci.yml`. Триггеры — **`pull_request` → `dev`/`main`**
(гейт перед мержем: `dev` — интеграционная ветка) и **`push` → `dev`/`main`** (пост-мерж + публикация
образа). Джобы: `backend` (go build/vet/test + golangci-lint), `flutter`
(build_runner → analyze → test → build apk), `docker` (сборка `apps/backend/Dockerfile` → **GHCR**,
только на push). Версии инструментов **зафиксированы** (детерминизм). Фиче-ветки отдельно не гоняем —
их вершину покрывает событие `pull_request`; `concurrency` отменяет устаревшие прогоны.

Реестр — **GHCR** (`ghcr.io`): встроен в Actions, бесплатен для репозитория, без внешних секретов
(логин через `GITHUB_TOKEN`).

## Последствия
- **+** Зелёный/красный статус на каждом PR; образ собирается из проверенного и влитого кода.
- **−** Жёсткая блокировка красного мержа (branch protection) на приватном free-тарифе GitHub
  **не enforced** — пока самодисциплина, до перехода на Pro (см. `docs/p0-08.md`).

## Обновление (path-фильтры)
Единый `ci.yml` разбит на два workflow с нативными path-фильтрами:
- **`ci-backend.yml`** (`paths: apps/backend/**`) — джобы `backend` + `docker`;
- **`ci-flutter.yml`** (`paths: apps/craft_wms/**`) — джоба `flutter`.

Backend-задача больше не пересобирает Flutter (и наоборот) — экономия времени на самом долгом
шаге (сборка APK). Джоба `docker` теперь `needs: [backend]` (образ бэкенда от Flutter не зависит).
⚠ При будущем branch protection «required checks» пропущенные по path-фильтру джобы могут «зависать»
как ожидаемые — решать при переходе на Pro (skipped=успех / gate-джоба).
