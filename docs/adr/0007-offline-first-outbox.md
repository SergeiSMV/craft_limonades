# ADR-0007 · Offline-first + Outbox + идемпотентность по `operation_id`

**Статус:** Планируется (реализация — фаза P2)

## Контекст
На складе связь нестабильна. Операции (приёмка, размещение, перемещение) не должны теряться при
пропаже сети и не должны двоиться при переотправке.

## Решение
Устройство работает **offline-first**. Каждая операция сперва пишется в **локальную очередь (Outbox,
drift/sqlite)** с уникальным **`operation_id`** и статусом; переживает перезапуск приложения. Движок
синхронизации отправляет очередь на бэкенд при появлении сети (ретраи с backoff). Бэкенд **дедуплицирует**
входящие батчи по `operation_id` в транзакции — повторная отправка не создаёт дублей. Сервер возвращает
статус (accepted/rejected + причина); отклонённые видны на устройстве и локально откатываются.

## Последствия
- **+** Работа без сети; надёжная доставка операций; переотправка безопасна (идемпотентность).
- **+** Второй рубеж дедупа (внешний ИД в 1С) не нужен — REST-обмена с 1С нет (см. [ADR-0004](0004-obmen-1c-excel-email.md)).
- **−** Сложность клиента (локальная БД, очередь, синхронизация, разрешение статусов) — основной объём P2.
- **−** Возможны временные расхождения «устройство ↔ сервер» до синхронизации.
