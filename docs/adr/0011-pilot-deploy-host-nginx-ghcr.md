# ADR-0011 · Пилотный деплой: хостовый nginx + образ из GHCR

**Статус:** Принято (P1-D · ранний пилотный деплой)

## Контекст
Каркас бэкенда готов уже к фазе P1 (auth + справочники + остатки), и есть сервер со статическим
доступом (домен `craft.skogi.ru`, за NAT, проброс 80/443). ТСД ходит на сервер **через интернет** —
значит TLS обязателен. Сервер уже держит другие сайты через **системный (хостовый) nginx** с
выпуском сертификатов через **certbot** (Let's Encrypt). Роадмап откладывал прод на P7, но выгодно
поднять деплой рано — обкатать TLS/секреты/CD на «пустом» приложении, пока ставки низкие, чтобы к
реальным операциям (P4+) деплой был решённой задачей.

## Решение
- **Reverse-proxy и TLS — на ХОСТОВОМ nginx, а не в контейнере.** Прод-стек (`docker-compose.prod.yml`)
  = только `postgres` + `backend`; backend публикуется на **loopback** (`127.0.0.1:8080`), наружу не
  смотрит. Хостовый nginx проксирует `craft.skogi.ru` → `127.0.0.1:8080`. Это не плодит второй прокси
  и переиспользует уже работающий certbot. (В dev остаётся контейнерный nginx — оправданная разница.)
- **Backend — готовым образом из GHCR** (`ghcr.io/<owner>/craft-wms-backend:<тег>`), не сборка на месте.
  Обновление = `docker compose pull && up -d` + миграции.
- **Миграции/сид в проде — без Go на сервере.** Бинарники `migrate` и `seed` встроены в образ (миграции
  `.sql` уже вшиты через `embed.go`), запускаются разовыми `docker compose run`.
- **Полная параметризация через `infra/.env.prod`** (в `.gitignore`). Один и тот же код/скрипты работают
  на любом сервере (сейчас — свой, потом — сервер заказчика); меняется только `.env.prod`. Vhost nginx
  генерируется из шаблона через `envsubst`.
- **Установка «в одну команду».** Рабочая раскладка на сервере: `/opt/craft-wms/.env.prod` (секреты,
  руками, вне git) + `/opt/craft-wms/app/` (git clone). Идемпотентные скрипты `deploy/`: `install.sh`
  (ПО → nginx+TLS → up+migrate+seed → включение авто-обновления — всё из `.env.prod`), `update.sh`
  (pull → up → migrate, идемпотентно), `pg-backup.sh`; общая логика — в `_lib.sh` (единый парсер
  `.env.prod` со срезкой inline-комментариев).
- **Авто-обновление (CD) — pull-моделью:** systemd-таймер на сервере периодически (`UPDATE_INTERVAL`,
  дефолт 5 мин) запускает `update.sh` и подтягивает новый образ `:main`. Push-модель (GitHub Actions
  по SSH) отвергнута — не хотим открывать наружу SSH-секреты и держать сервер достижимым для CI.
  Прод отслеживает тег `:main`: релиз = мерж `dev → main` → CI собирает `:main` → сервер сам обновляется.
- **Postgres наружу не публикуется**; backend — только на loopback. Секреты — в `.env.prod` (root-only), не в git.

## Последствия
- **+** Ранняя обкатка инфраструктуры; TLS/CD решены до реальных данных.
- **+** Портируемость: заказчик разворачивает тем же кодом, заполнив свой `.env.prod`.
- **+** Минимум движущихся частей: TLS отдаётся уже настроенному certbot, без контейнеров-прокси.
- **−** Разница dev/prod (контейнерный nginx vs хостовый) — держим в голове при отладке.
- **−** Приватный образ GHCR требует токена; чтобы этого избежать — рекомендуем сделать GHCR-пакет публичным
  (образ секретов не содержит; конфигурация приходит из `.env.prod` в рантайме).
- **−** Авто-обновление тянет `:main` без ручного подтверждения: непроверенная миграция может уйти на прод —
  приемлемо для соло-пилота (мержи контролирует разработчик); строгий gated-CD — на P7.
- **−** P7 остаётся для финального ужесточения (мониторинг, ротация логов контейнеров, секрет-менеджер).
