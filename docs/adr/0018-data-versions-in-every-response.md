# ADR-0018 · Свежесть данных: версии областей в каждом ответе, без опроса

**Статус:** Принято (ADHOC-60). Уточняет [ADR-0014](0014-transport-http-outbox-polling.md) в
части «актуальность — на polling».

## Контекст
ТСД и портал держат данные у себя: справочники и снимок склада — в локальной базе ТСД, списки
— в состоянии страниц портала. Узнать, что их пора перечитать, клиенту было неоткуда: свежесть
держалась на входе, «потянуть вниз» и открытии экрана. ADR-0014 предлагал опрос при активном
экране, но опрос по таймеру сажает батарею ТСД, а WebSocket и брокер отвергнуты там же.

При этом клиенты обращаются к серверу постоянно: открывают экраны, отправляют очередь операций,
берут задания. Каждое такое обращение может само принести ответ «что изменилось».

## Решение
**Сервер отдаёт версии областей данных заголовком в каждом ответе API; клиент перечитывает только
области, чья версия разошлась с его. Фонового опроса нет.**

- **Области** — единицы перечитывания на клиентах, а не таблицы: `goods` (номенклатура, группы,
  поставщики, штрихкоды), `cells` (склады, ячейки, стеллажи), `settings` (внутренние склады,
  причины проблем, должности, пользователи), `contents` (остатки, партии, короба, марки ЧЗ),
  `tasks` (задания и их ход), `problems`, `stocktakes`, `documents`. Таблица может входить в
  несколько областей (пересчёт — и `tasks`, и `stocktakes`).
- **Версия — счётчик** в `data_versions`, не время: у времени совпадения и расхождения часов, а
  последовательность видна до фиксации транзакции.
- **Счётчик повышает триггер уровня оператора** на таблицах области, в транзакции правки: версию
  не увидеть раньше данных, откат откатывает и её. Оператор, не изменивший строк (охранный
  `UPDATE … WHERE`), счётчик не трогает — по таблице переходов.
- **Заголовок `X-Data-Versions`** («contents=340,goods=12,…») ставит middleware в момент записи
  ответа — после транзакции обработчика. Поэтому ответ на свою операцию уже несёт версию после
  неё: перечитывание после своей правки клиент делает один раз и сразу, а не на следующем
  ответе. На ТСД оно сливается с обновлением снимка после подтверждения очереди — одна загрузка.
- **Клиент** сравнивает версии из каждого ответа со своими и перечитывает только разошедшиеся
  области — в фоне, одна загрузка области за раз. Первый ответ после запуска лишь запоминает
  версии: загрузку при входе клиент делает и так.
- **Без опроса.** Свежесть приходит только с обращениями, которые клиент делает сам. ТСД, лежащий с
  открытым экраном без действий, остаётся на прежних данных до следующего действия — для склада
  это норма.

## Последствия
- Плюс: изменения, сделанные другим терминалом или офисом, доходят при ближайшем обращении, без
  батареи на опрос и без постоянного соединения.
- Цена: один `SELECT` по крошечной таблице на каждый ответ API; строка-счётчик области — общая
  блокировка для пишущих в эту область транзакций (до фиксации). На пилоте не заметно.
- Перечитывание области — целиком: сдвиг `contents` перечитывает весь снимок склада (риск 3,
  `dev-context.md` §10).

## На рост (не сделано сознательно)
- Дельта снимка: версия у строки и `GET /contents/snapshot?since=<версия>`.
- Если строка-счётчик станет узким местом — журнал изменений вставками вместо `UPDATE` одной
  строки.
