# P1-D4 · Самообновление деплоя: одна команда на сервере

**Статус:** готово (ветка `p1-d4-deploy-self-update`); ⚠ на прод-сервере ещё не применял.
**Фаза:** вне фаз — операционная задача, продолжение P1-D2/P1-D3.

## Задача

Установка таймеров P1-D3 на сервере требовала от администратора пяти команд подряд: `git pull`,
затем четыре строки `sed`/`tee`/`systemctl`. Это нарушало планку, заданную в P1-D2, — «установка
в одну команду».

Корень был не в отсутствии скрипта, а в том, что **авто-обновление тянуло только образ из GHCR**:
`update.sh` не обновлял ни себя, ни systemd-юниты. Правки в `deploy/**` лежали в git и не доезжали
до сервера, поэтому каждое изменение требовало ручной раскладки.

## Критерий готовности

Администратору достаточно одной команды; правки скриптов и юнитов доезжают на сервер сами;
неудачное обновление видно в journal, а не по жалобе кладовщика утром.

## Решения (согласованы с заказчиком)

Обсуждался вопрос: обновлять код деплоя автоматически или оставить ручным шагом. Довод «сломанный
скрипт упадёт в обоих случаях, человек диффа не читает» — принят: от багов защищает `ci-deploy.yml`,
а не нажатие Enter. Автообновление кода деплоя **включено**, но с двумя страховками, которые
закрывают то, что человек в цикле действительно давал:

- **Падение в 3 ночи обнаруживается только утром.** Закрыл проверкой `/ready` после обновления
  и записью в journal с приоритетом error (`<3>`) — падение видно в `systemctl status` красным.
- **Сломанный `update.sh` рвёт сам механизм доставки починки.** Закрыл перезапуском скрипта
  из временной копии до `git pull`.

## Что сделано

### `update.sh` — обновление сервера целиком

Порядок: самокопирование → `git pull` → переустановка юнитов → образ + миграции → `/ready`.

**Самокопирование.** `bash` дочитывает скрипт с диска по мере выполнения, поэтому `git pull`,
переписав файл на ходу, привёл бы к исполнению смеси старой и новой версии. Скрипт копирует
`deploy/*.sh` во временный каталог и перезапускает себя оттуда (`CRAFT_SELF_COPY=1`), передавая
настоящий корень репозитория через `CRAFT_REPO_ROOT` — иначе пути к compose, `.env.prod` и юнитам
указывали бы на копию. Копия убирается через `trap … EXIT`.

Следствие, задокументированное в [prod-deploy.md](../deploy/prod-deploy.md): правки в самом `update.sh` вступают в силу
со **следующего** запуска. Это и есть защита — сломанная версия не может оборваться на середине
собственного обновления.

**`git pull`** идёт с `-c safe.directory=$REPO_ROOT` (таймер работает от root, а клон принадлежит
пользователю сервера — без этого git отказывается работать с «чужим» репозиторием) и с `--ff-only`
(при локальных правках лучше не тронуть боевой сервер, чем молча смержить). Неудача `git pull`
не прерывает обновление: пишется в journal как error, работа продолжается со старым кодом деплоя.

**Проверка `/ready`,** а не `/health`: первый щупает БД, и после миграций важна именно связность
с базой. 20 попыток с паузой 3 с, затем `journal_err` + выход с ошибкой.

### `_lib.sh` — общие функции

- **`install_systemd_units()`** — установка юнитов вынесена из `install.sh` и переиспользуется
  в `update.sh`. Без этого раскладка юнитов дублировалась бы в двух скриптах.
- **`health_check()`** — проверка готовности.
- **`journal_err()`** — запись с префиксом `<3>`: systemd читает его как приоритет error, и
  падение ночного таймера видно в `systemctl status` красным.
- `REPO_ROOT` научился читать `CRAFT_REPO_ROOT` (для запуска из копии).
- `CRAFT_SYSTEMD_DIR` — тестовый шов: позволяет разложить юниты в каталог без root и проверить
  подстановку плейсхолдеров.

### Прочее

- `install.sh` — свои блоки установки таймеров заменены вызовом `install_systemd_units()`.
- `.env.prod.example` — флаг `SELF_UPDATE` (по умолчанию `true`).
- `ci-deploy.yml` — проверка плейсхолдеров теперь ищет подстановку во всех `deploy/*.sh`,
  а не только в `install.sh` (подстановки переехали в `_lib.sh`).
- [`deploy/prod-deploy.md`](../deploy/prod-deploy.md) — раздел авто-обновления переписан.

## Проверка

Прогон на заглушках (`docker`, `git`, `systemctl`, `curl` подменены в `PATH`; юниты
раскладывались в каталог через `CRAFT_SYSTEMD_DIR`):

| Сценарий                      | Результат                                  |
|-------------------------------|--------------------------------------------|
| Полный прогон `update.sh`     | прошёл целиком до `/ready` 200             |
| Содержимое разложенных юнитов | корень репо подставлен верно               |
| Временная копия               | удалена после выхода (`trap`)              |
| `/ready` не отвечает          | ошибка в journal, ненулевой код возврата   |
| `SELF_UPDATE=false`           | код деплоя не трогается, образ обновляется |
| `shellcheck -S warning -x`    | 0 issues                                   |

Подробности по строкам:

- **Полный прогон** — самокопирование → `git pull` → установка юнитов → образ → миграции →
  проверка `/ready`.
- **Юниты** — `ExecStart` и `WorkingDirectory` указывают на настоящий корень репозитория,
  а не на временную копию; неподставленных плейсхолдеров не осталось.
- **`/ready` не отвечает** — в journal уходит `<3>[update] backend не отвечает…`, скрипт
  возвращает ненулевой код.
- **`shellcheck`** гонялся в контейнере `koalaman/shellcheck:stable`.

Попутно `shellcheck` поймал неиспользуемую переменную цикла в `health_check` — заменено на
`while (( attempts-- > 0 ))`.

## Что делать на сервере

Разово, чтобы доставить сам этот механизм (дальше он обновляется сам):

```bash
ssh sergeismv@192.168.0.106
cd /opt/craft-wms/app && git pull
sudo bash deploy/update.sh
```

Третья команда поставит таймеры P1-D3 (бэкап + проверка восстановимости) и проверит `/ready`.
После этого любое изменение в `deploy/**` доезжает на сервер само.

## Границы

- Автоматического отката при неуспешной проверке `/ready` нет: обновление применяется, ошибка
  громко логируется. Откат — ручной, по журналу.
- `update.sh` не следит за изменениями `.env.prod` — секреты по-прежнему кладутся руками.
- Правки в самом `update.sh` применяются со следующего запуска (осознанное следствие
  самокопирования).
