# P1-D3 · Бэкап и восстановление прод-БД

**Статус:** готово (ветка `p1-d3-db-backup-restore`); ⚠ на прод-сервер ещё не ставил.
**Фаза:** вне фаз — операционная задача из списка «📌 обязательно перед пилотом».

## Задача

Бэкап прод-БД существовал наполовину: скрипт `deploy/pg-backup.sh` (дамп + ротация) был, но
**не был повешен на расписание, не имел процедуры восстановления и ни разу не проверялся**.
После отказа от e-mail (ADR-0013) почтовый ящик перестал быть внешним архивом отчётов, и БД
осталась единственной копией данных — поэтому пункт и был повышен до обязательного перед пилотом.

Нужно: расписание, восстановление из дампа, полный прогон цикла бэкап→restore.

## Критерий готовности

Бэкап идёт сам; есть скрипт восстановления; цикл «дамп → потеря данных → восстановление» пройден
целиком, а не описан на бумаге.

## Решения (согласованы с заказчиком)

- **Запуск по расписанию — systemd-таймеры, а не cron**, как и у авто-обновления: их ставит
  `install.sh`, они видны в `systemctl list-timers`, логи идут в journal.
- **Проверка восстановимости — регулярная и автоматическая:** отдельный таймер разворачивает
  свежий дамп во временную базу.

## Что сделано

### `deploy/pg-restore.sh` — восстановление (новый)

Два режима:

- **`--check [файл]`** — безопасная проверка. Разворачивает дамп во временную базу
  `craft_wms_restore_check`, сверяет состав, удаляет её. Прод-база и backend не затрагиваются.
  Временная база удаляется через `trap … EXIT` — в том числе если прогон упал, иначе она осталась
  бы занимать место.
- **`[файл]`** — боевое восстановление, замещает прод-базу.

Без аргумента берётся самый свежий дамп из `BACKUP_DIR`.

**Порядок боевого восстановления** (важен: каждый шаг отсекает ошибку до необратимого):

1. `gzip -t` — целостность архива. Битый дамп ловится **до** остановки backend.
2. Подтверждение вводом имени базы (`--yes` пропускает — для скриптов).
3. **Страховочный дамп текущего состояния** → `pre-restore-*.sql.gz`. Если он пустой — выход,
   прод не тронут. Это спасает от «восстановили не тот дамп».
4. Остановка backend + `pg_terminate_backend` для отвисших соединений: пока есть подключения,
   базу не удалить.
5. `DROP DATABASE` / `CREATE DATABASE` → разворот дампа.
6. Проверка состава (см. ниже) → запуск backend.

**Проверка состава (`verify`)** — общая для обоих режимов, чтобы «успешно развернулось» не означало
пустышку:

- все 13 таблиц на месте (12 доменных + `schema_migrations`);
- `schema_migrations.dirty = false` — иначе дамп снят с БД в незавершённой миграции;
- в `users` есть хотя бы одна строка — иначе войти в систему будет нельзя;
- печатает число строк по ключевым таблицам.

`psql` везде с `-v ON_ERROR_STOP=1`: без него psql проглатывает ошибки SQL и возвращает 0, и
битый дамп прошёл бы за успешный.

### Расписание — systemd

Новые юниты в `deploy/systemd/`, по образцу `craft-wms-update`:

| Юнит                      | Действие                | По умолчанию                                 |
|---------------------------|-------------------------|----------------------------------------------|
| `craft-wms-backup`        | `pg-backup.sh`          | ежедневно 03:30 (`BACKUP_SCHEDULE`)          |
| `craft-wms-restore-check` | `pg-restore.sh --check` | воскресенье 04:30 (`RESTORE_CHECK_SCHEDULE`) |

У обоих `Persistent=true` — сервер это ноутбук, его выключают; без этого пропущенный день остался
бы без дампа. `install.sh` ставит таймеры при `AUTO_BACKUP≠false`; флаг **отдельный** от
`AUTO_UPDATE`: авто-обновление можно не хотеть, а бэкап нужен всегда. При `AUTO_BACKUP=false`
скрипт печатает предупреждение, что БД остаётся единственной копией.

Новые переменные в `infra/.env.prod.example`: `AUTO_BACKUP`, `BACKUP_SCHEDULE`,
`RESTORE_CHECK_SCHEDULE`, `KEEP_DAYS`.

## Проверка — полный цикл пройден вживую

Стенд: `postgres:16-alpine` из **прод-compose** (`infra/docker-compose.prod.yml`) на Colima,
временный `.env.prod`, схема накачена всеми миграциями `000001`–`000007` + посев (пользователь,
склад, ячейка, товар, партия, остаток).

| Сценарий                                                          | Результат                                                                          |
|-------------------------------------------------------------------|------------------------------------------------------------------------------------|
| `pg-backup.sh`                                                    | дамп создан, ротация отработала                                                    |
| `pg-restore.sh --check`                                           | развернулось, 13 таблиц, версия миграций 7, строки сошлись, временная база удалена |
| Потеря данных (`DELETE FROM goods/stock`) → `pg-restore.sh --yes` | данные вернулись (`goods=1 stock=1 users=1`), страховочный дамп создан             |
| Неверное подтверждение                                            | прервано, ничего не изменено                                                       |
| Битый архив (обрезанный gzip), оба режима                         | отсечён на проверке целостности, **прод-база цела**                                |

Окружение возвращено: стек снят с `-v`, Colima остановлена.

## Команды проверки

```bash
bash -n deploy/pg-restore.sh && bash -n deploy/install.sh     # синтаксис

colima start
# стенд: db из прод-compose + временный .env.prod, миграции + посев
CRAFT_ENV_FILE=/tmp/.env.prod BACKUP_DIR=/tmp/backups bash deploy/pg-backup.sh
CRAFT_ENV_FILE=/tmp/.env.prod BACKUP_DIR=/tmp/backups bash deploy/pg-restore.sh --check
CRAFT_ENV_FILE=/tmp/.env.prod BACKUP_DIR=/tmp/backups bash deploy/pg-restore.sh --yes
colima stop
```

## Границы и что осталось

- ⚠ **На прод-сервере ничего не устанавливалось.** Таймеры появятся после `git pull` в
  `/opt/craft-wms/app` и повторного `install.sh` (идемпотентен), либо ручной установкой юнитов.
  Нужен доступ по SSH из локальной сети; ещё не делал.
- ⚠ **Дампы лежат на том же диске, что и БД.** От отказа диска это не спасает: нужна копия вовне
  (внешний диск / другой хост / облако). Отдельный вопрос, в объём не входил.
- Восстановление на момент времени (PITR, WAL-архив) не вводили: для пилота с суточным дампом
  избыточно.
- Шифрование дампов не вводили — в них персональные данные сотрудников (ФИО, логины).
  Стоит вернуться перед боевой эксплуатацией.
