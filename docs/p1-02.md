# P1-02 · Схема БД: партии (batches) и остатки (stock)

**Статус:** ✅ схема готова, Runtime-проверка зелёная (up → down → up, инварианты, составной FK). Кода Go не добавлялось — только миграция (domain остатка — P1-03; repository/CRUD — P1-06).
**Задача:** `batches` (партия = товар + дата выпуска), `stock` (остаток в разрезе ячейка × товар × партия → количество), индексы под запрос «где и сколько товара X».
**Критерий готовности:** остаток хранится по партиям; целостность (нельзя завести остаток с товаром, не совпадающим с партией; нельзя увести в минус); запросы по товару быстрые.

---

## Что сделано

- **`migrations/000004_batches_stock.up.sql`** — две таблицы + индексы + триггеры `updated_at` (переиспользуют `set_updated_at()` из `000001`):
  - **`batches`** — `id uuid PK`, `good_id → goods`, `production_date date NOT NULL`, timestamps. `UNIQUE(good_id, production_date)` — одна партия товара на дату. Плюс `UNIQUE(id, good_id)` — цель составного FK из `stock`.
  - **`stock`** — `id uuid PK`, `cell_id → cells`, `good_id`, `batch_id`, `qty numeric(20,3) NOT NULL CHECK (qty >= 0)`, timestamps. `UNIQUE(cell_id, good_id, batch_id)` — грань учёта. Составной FK `(batch_id, good_id) → batches(id, good_id)`. Индексы `stock_good_id_idx`, `stock_batch_id_idx`.
- **`migrations/000004_..._down.sql`** — `DROP TABLE IF EXISTS` в обратном FK-порядке (stock → batches).

### Ключевые решения

- **Партия = (товар, дата выпуска).** Крипто-маркировки нет — партия простая. `production_date NOT NULL` (дата выпуска при приёмке всегда есть). `UNIQUE(good_id, production_date)` — повторная приёмка той же партии не двоит запись.
- **`stock.good_id` денормализован (вариант A).** Товар выводится из `batch_id` (через `batches.good_id`), но `good_id` держим прямо в `stock` — запрос «где и сколько товара X» идёт по индексу `stock_good_id_idx` **без join к `batches`** (это самый горячий запрос всего учёта).
- **Согласованность гарантирует составной FK** `(batch_id, good_id) → batches(id, good_id)`: партия должна существовать **и** её товар обязан совпадать со `stock.good_id`. Исключает рассинхронизацию денормализованного поля на уровне БД. Ради этого на `batches` заведён `UNIQUE(id, good_id)` (цель FK). Валидность `good_id` обеспечивается транзитивно (`batches.good_id → goods`), поэтому отдельный FK `stock.good_id → goods` не нужен.
- **`qty numeric(20,3)`** — дробное для `uom='кг'`; `CHECK (qty >= 0)` — backstop против ухода остатка в минус (атомарность движений — P1-03).
- **Индексы:** грань `UNIQUE(cell_id, good_id, batch_id)` ведущим `cell_id` обслуживает «что лежит в ячейке»; отдельный `stock_good_id_idx` — «где товар X»; `stock_batch_id_idx` — остатки партии и обслуживание составного FK. Индекс по `batches.good_id` не нужен — `UNIQUE(good_id, production_date)` уже ведущий по `good_id`.

## Границы задачи

- **Только схема (миграция).** Атомарные приход/расход остатка в транзакциях — **P1-03**. Repository/CRUD/поиск, API остатков — **P1-06**; Flutter-экран остатков — **P1-07**.
- **CHECK `qty >= 0`** — статический backstop; защита от гонок (два параллельных списания) обеспечивается транзакциями P1-03, нагрузочно проверяется в P7-02.
- **Грузовые единицы (ГЕ).** `stock` хранит штучный/россыпной остаток по ячейкам; состав ГЕ (`load_units`/`lu_content`) — отдельная схема P4-01, поверх этой.

## Проверка

Runtime против живого Postgres — только он подтверждает применимость схемы и инварианты.

```bash
# из корня проекта
colima start && make up

# полный цикл миграции: накат → откат (все) → накат обратно.
# NB: раннер печатает только строку `migrate <cmd>: ok`; состояние после стрелки (→)
# в stdout НЕ выводится — это результат в БД, проверяется отдельным SELECT ниже.
make migrate-up          # печатает: migrate up: ok    (→ в БД: все миграции накачены)
make migrate-down        # печатает: migrate down: ok  (→ в БД: остаётся только schema_migrations)
make migrate-up          # печатает: migrate up: ok    (→ в БД: version = 4, dirty = f)
make seed                # вернуть бейдж-админа после полного отката

# проверка состояния и структуры (креды БД из .env; кавычки обязательны — иначе psql примет "-d" за роль)
set -a && . ./.env && set +a
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" infra-db-1 \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version, dirty FROM schema_migrations;"  # → 4 | f
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" infra-db-1 \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\d batches"   # UNIQUE(good_id,production_date), UNIQUE(id,good_id)
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" infra-db-1 \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\d stock"     # UNIQUE(cell,good,batch), составной FK, CHECK qty>=0

make down && colima stop  # остановка
```

Проверено вживую (2026-07-21):
- **up → down → up** — все три `ok`; после отката остаётся только `schema_migrations`, после повторного наката — `version = 4, dirty = f`.
- **Инварианты (смоук):** корректный остаток проходит; **составной FK отклоняет** остаток с `good_id`, не совпадающим с товаром партии; дубль грани `(cell, good, batch)` отклонён; `qty = -1` отклонён (`stock_qty_check`); дубль партии `(good, production_date)` отклонён; дробное `qty = 12.345` для `uom='кг'` проходит.
- **Статика:** `go build ./...` и `go vet ./...` — чисто (миграции встраиваются через `migrations/embed.go`).

> ⚠️ `make migrate-down` откатывает **все** миграции (раннер без шагов) — на dev сносит и `users`; сид-админа возвращает `make seed`. На проде откат так не делают.
