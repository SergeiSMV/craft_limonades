### Схема v0

```sql
users(     id uuid PK default gen_random_uuid(),
           login varchar(8) NOT NULL UNIQUE CHECK (login ~ '^[0-9]{8}$'),
           password_hash text NOT NULL, full_name text NOT NULL,
           role text NOT NULL DEFAULT 'employee' CHECK (role IN ('employee','admin')),
           is_active boolean NOT NULL DEFAULT true,   -- блокировка/«удаление» = is_active=false
           created_at, updated_at timestamptz NOT NULL DEFAULT now() )   + триггер updated_at

audit_log( id bigint GENERATED ALWAYS AS IDENTITY PK,
           user_id uuid REFERENCES users(id),  action text NOT NULL,
           entity_type text, entity_id text, details jsonb,
           created_at timestamptz NOT NULL DEFAULT now() )               + индексы (user_id),(created_at),(entity_type,entity_id)
```

### Ключевые решения

- **Драйвер — pgx v5 + pgxpool** (без sqlx): нативно под Postgres, свой пул, скан в структуры через `pgx.RowToStructByName`.
- **`gen_random_uuid()`** встроен в Postgres 16 — расширение не нужно.
- **`login`** ограничен на уровне БД: `varchar(8)` + `CHECK ^[0-9]{8}$` (8 цифр из бейджа).
- **Роли `employee` / `admin`** (`role text + CHECK`, дефолт `employee`). Отход от плана v3 («ролей нет») — под будущее управление пользователями (добавить/заблокировать/«удалить») из Flutter-приложения. Enforcement и сид-админ с ролью — в P0-04.
- **Блокировка и «удаление» пользователя = `is_active=false`** (мягко): запись и связи с `audit_log` сохраняются, история не рвётся.
- **`audit_log`** минимальный + `details jsonb` (device_id / operation_id кладём в jsonb, выделим в колонки позже).
- **Миграции применяются явной командой** (`make migrate-up`), не на старте сервиса — безопаснее при нескольких инстансах. `.sql` встроены в бинарь (`embed`), драйвер БД для migrate — схема `pgx5://` (раннер сам приводит `postgres://` → `pgx5://`).
- **`/health` (liveness) отделён от `/ready` (readiness)**: процесс может быть жив, а БД — недоступна; это разные состояния. Сервис не падает, если БД недоступна на старте (пишет warn), — контейнер не флапает из-за кратких сбоев БД.

## Запуск и проверка критериев готовности

Требуется поднятый стек (`make up`) — БД публикуется на `localhost:${POSTGRES_PORT}`.
Миграции выполняются **из корня проекта**.

### 1. Накат миграций (up)

```bash
make migrate-up
```
Ожидаемо: `migrate up: ok`. Проверка схемы:
```bash
docker exec infra-db-1 psql -U wms -d craft_wms -c "\dt"        # users, audit_log, schema_migrations
docker exec infra-db-1 psql -U wms -d craft_wms -c "\d users"   # колонки, UNIQUE, CHECK, триггер
```

### 2. Откат миграций (down)

```bash
make migrate-down
docker exec infra-db-1 psql -U wms -d craft_wms -c "\dt"        # остаётся только schema_migrations
```
Ожидаемо: `migrate down: ok`; `users` и `audit_log` удалены.

### 3. Повторный накат (идемпотентность потока)

```bash
make migrate-up
docker exec infra-db-1 psql -U wms -d craft_wms -tAc \
  "SELECT count(*) FROM information_schema.tables WHERE table_name IN ('users','audit_log');"   # 2
```

### 4. Подключение к БД по HTTP (`/ready`)

```bash
curl -s -w " [HTTP %{http_code}]\n" http://localhost:8080/health   # {"status":"ok"}    liveness
curl -s -w " [HTTP %{http_code}]\n" http://localhost:8080/ready    # {"status":"ready"} readiness (ping БД)
```
Лог backend при старте: `"msg":"database connected"` (`docker logs infra-backend-1`).
