# P1-03 · Domain stock: атомарные приход/расход остатка

**Статус:** ✅ код готов, весь контур зелёный (build/vet, gofmt, golangci-lint 0 issues, юнит + integration + `-race`).
**Задача:** доменный слой движения остатка — **приход** (увеличить) и **расход** (уменьшить) по грани `(ячейка, товар, партия)` с гарантией атомарности: два параллельных списания не уводят остаток в минус и не теряются. Ядро всех операций (приёмка/размещение/перемещение).
**Критерий готовности:** конкурентные операции не ломают остаток (проверено интеграционным конкурентным тестом; нагрузочно — P7-02).

---

## Что сделано

- **`internal/model/stock.go`** — `StockKey{CellID, GoodID, BatchID}` (грань учёта) и `Stock` с `Qty decimal.Decimal` (точные дробные количества для `uom='кг'`, не float).
- **`internal/repository/postgres.go`** (+) — интерфейс `Querier` (реализуют и `*pgxpool.Pool`, и `pgx.Tx`) + хелпер `WithinTx(ctx, pool, fn)` (BEGIN→fn→COMMIT / ROLLBACK). Даёт транзакционную композицию нескольких движений.
- **`internal/repository/stock.go`** — `StockRepository`:
  - `Add` — приход: `INSERT … ON CONFLICT (cell,good,batch) DO UPDATE SET qty = stock.qty + EXCLUDED.qty` (атомарный upsert);
  - `Remove` — расход: `UPDATE … SET qty = qty - $ WHERE … AND qty >= $`; 0 затронутых строк → `ErrInsufficientStock`;
  - `Transfer` — расход из `from` + приход в `to` в **одной транзакции** (примитив для P5/P6);
  - `GetQty` — текущее количество (нет строки → 0).
- **`internal/service/stock.go`** — `StockService`: `Receive` / `Issue` / `Transfer` (валидация `qty>0` → `ErrInvalidQuantity`; маппинг `repository.ErrInsufficientStock` → доменной `service.ErrInsufficientStock`).
- **Тесты:**
  - `internal/service/stock_test.go` — юнит на fake-repo: валидация количества, вызовы репозитория, маппинг ошибок (без БД);
  - `internal/repository/stock_integration_test.go` — **testcontainers** (реальный Postgres): upsert-приход (вкл. дробное), guard-расход, атомарный `Transfer` с откатом, и ⚠ **конкурентный тест** (200 горутин × расход 1 из остатка 100 → ровно 100 успехов, 100 отказов, итог 0, минуса нет).

### Ключевые решения

- **Атомарность — на атомарном SQL, без `SELECT FOR UPDATE`.** Инкремент (upsert) и декремент (`UPDATE … WHERE qty >= $`) — каждый один стейтмент, race невозможен; `CHECK(qty>=0)` из схемы (P1-02) — страховка. Явные блокировки не нужны.
- **`qty` — `decimal.Decimal`** (shopspring), не float: количества дробные и должны быть точными. На границе SQL передаём строкой (`$::numeric`), читаем `qty::text` → `decimal` — без потерь и без завязки на кодирование типов pgx.
- **Нулевой остаток — строку не удаляем** (guard оставляет `qty=0`); запросы «где товар» фильтруют `qty>0`, следующий приход апсертит ту же строку.
- **Транзакции внутри репозитория** (`Transfer` через `WithinTx`), сервис — тонкий (валидация + маппинг). `Querier`-абстракция открыта для будущей кросс-репозиторной композиции (приёмка P4 и т.д.).
- **Ошибки:** `repository.ErrInsufficientStock` (raised в `Remove`) → сервис маппит в `service.ErrInsufficientStock`, чтобы вызывающие (хендлеры P1-06) не зависели от слоя repository.

- **Только домен остатка.** HTTP-эндпоинты — P1-06; импорт номенклатуры/ячеек — P1-04/05; UI перемещения/пополнения — P5/P6 (встают на `Transfer`/`Receive`/`Issue`).

cd apps/backend
