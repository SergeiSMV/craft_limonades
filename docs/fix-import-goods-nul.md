# Fix · Импорт номенклатуры падал на NUL-байте (0x00) в ячейке

**Статус:** готово (ветка `fix-import-goods-nul-bytes`). Затрагивает импорт номенклатуры (P1-04).

## Симптом

Загрузка реальной выгрузки 1С `Мясные снеки.xls` через портал падала:

```
Ошибка: не удалось импортировать: upsert good "14900":
ERROR: invalid byte sequence for encoding "UTF8": 0x00 (SQLSTATE 22021)
```

## Причина

`extrame/xls` иногда протаскивает в значение ячейки **нулевой байт `0x00`** — остаток UTF-16-паддинга
исходного бинарного `.xls`. `strings.TrimSpace` его не убирает (это не пробельный символ), и строка с
`0x00` уходила в `INSERT`. **Postgres не принимает `0x00` в колонке `text`** → `SQLSTATE 22021`,
вся транзакция импорта откатывалась.

## Исправление

`internal/importer/goods.go` — чистим управляющие байты при чтении ячейки:

- `stripControl(s)` выкидывает все управляющие руны (C0 `< 0x20`, включая NUL, и DEL `0x7f`); в
  значениях номенклатуры их быть не должно. Есть быстрый путь: если управляющих нет — строка как есть.
- `cellAt` теперь `TrimSpace(stripControl(row.Col(idx)))`; `norm` (заголовки) тоже прогоняется через
  `stripControl` — на случай мусора в шапке.

Демэнглинг кода-даты (`demangleCode`) не затронут: он работает поверх уже очищенного значения.

## Проверка

- Юнит `TestStripControl`: NUL внутри/в хвосте, прочие C0+DEL, чистый текст без изменений, табы/переводы
  строк убираются. Существующие тесты парсера (`Кальмары`, коды-даты) — зелёные. `go build`/`golangci-lint` 0.
- **Runtime на реальном файле** (тот, что падал): `POST /api/v1/import/goods` с `Мясные снеки.xls` →
  **HTTP 200**, `goods_created=67`, `groups=3`, `suppliers=4`, `skipped=0`. Повторный импорт →
  `updated=67` (идемпотентно). В БД товар `14900` — «Чипсы из свинины …», `0x00` в имени отсутствует.

```bash
cd apps/backend && go test ./internal/importer/ -count=1 && go build ./... && golangci-lint run ./internal/importer/...
# runtime: make up && make migrate-up && make seed → curl -F "file=@Мясные снеки.xls" .../import/goods
```

## Границы

- Фикс на стороне парсера номенклатуры (`.xls`). Импорт ячеек (`.xlsx`, `excelize`) этой проблеме не
  подвержен (другой формат/библиотека), но `excelize` отдаёт уже валидный UTF-8 — при необходимости
  ту же санитизацию легко перенести и туда.
