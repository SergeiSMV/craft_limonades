# P1-01 · Схема БД: справочники (warehouses, cells, goods, barcodes)

**Статус:** ✅ схема готова, Runtime-проверка зелёная (up → down → up, констрейнты, каскад). Кода Go не добавлялось — только миграция (repository/CRUD — P1-06).
**Задача:** справочные таблицы склада — склады, ячейки (адрес + тип «на вырост»), товары (внутренний ключ + бизнес-ключи из 1С, единица измерения), штрихкоды (товар 1→N ШК). **Зон нет** — ячейка принадлежит складу напрямую.
**Критерий готовности:** миграция накатывается/откатывается; таблицы, связи и ограничения соответствуют модели предметной области.

---

## Что сделано

- **`migrations/000003_goods_cells_barcodes.up.sql`** — четыре таблицы + индексы + триггеры `updated_at` (переиспользуют `set_updated_at()` из `000001`):
  - **`warehouses`** — `id uuid PK`, `code text UNIQUE`, `name`, `is_active`, timestamps. Пилот на одном складе, но справочник заводим сразу (от него адресуются ячейки).
  - **`cells`** — `id uuid PK`, `warehouse_id → warehouses`, `address`, `type` (дефолт `'storage'`), `is_active`, timestamps. **`UNIQUE(warehouse_id, address)`** — адрес уникален внутри своего склада; индекс `cells_warehouse_id_idx`.
  - **`goods`** — `id uuid PK` (внутренний), `external_id uuid` (1С-GUID, nullable), `code text` (артикул, nullable), `name`, `uom`, `is_active`, timestamps. **Partial-unique** `goods_external_id_key` на `external_id WHERE NOT NULL`; обычный индекс `goods_code_idx`.
  - **`barcodes`** — `id uuid PK`, `good_id → goods ON DELETE CASCADE`, `barcode text UNIQUE`, `symbology text NULL`, timestamps. Индекс `barcodes_good_id_idx`.
- **`migrations/000003_..._down.sql`** — `DROP TABLE IF EXISTS` в обратном FK-порядке (barcodes → goods → cells → warehouses).

### Ключевые решения

- **Ключ товара — внутренний суррогат `id`, а не 1С-GUID.** Ревизия плана v3 («ключ — GUID»): обмен с 1С идёт через **Excel, а не REST**, поэтому GUID в файле импорта **не гарантирован** (появится, только если его добавят колонкой в выгрузку — это открытый вопрос №1, формат импорта, P1-04). `external_id` (GUID) и `code` (артикул) живут рядом как **бизнес-ключи** для сверки и идемпотентного ре-импорта; какой из них станет ключом апсерта — решаем в P1-04, когда увидим файл.
- **`external_id` — partial-unique** (`WHERE external_id IS NOT NULL`): один GUID → один товар, но строки без GUID (NULL) не конфликтуют между собой.
- **`code` без UNIQUE** — 1С не гарантирует уникальность кода/артикула; ставим только индекс для поиска. Жёсткость добавим в P1-04 по факту формата.
- **`cells.type` — свободный `text` + дефолт `'storage'`, без CHECK.** Тип ячейки «на вырост»; допустимые значения устаканятся к приёмке/размещению (P4/P5), рано их цементировать.
- **`goods.uom` — строкой** (`'шт'`, `'кг'`), без отдельного справочника единиц — для пилота избыточен.
- **`barcodes.good_id ON DELETE CASCADE`** — ШК не существуют без товара; удаление товара уносит его штрихкоды.
- **Зон нет:** `cells.warehouse_id → warehouses.id` напрямую.

## Проверка

Runtime против живого Postgres — только он подтверждает, что схема применяется и констрейнты верны.

```bash
# из корня проекта
colima start && make up

# полный цикл миграции: накат → откат (все) → накат обратно
make migrate-up          # migrate up: ok  → schema_migrations.version = 3
make migrate-down        # migrate down: ok → остаётся только schema_migrations
make migrate-up          # migrate up: ok  → таблицы восстановлены, version = 3, dirty = f
make seed                # вернуть бейдж-админа после полного отката

# структура и ограничения. Сначала подхватываем креды БД из .env в текущую оболочку
# (иначе $POSTGRES_USER пуст → psql берёт "-d" за имя роли: FATAL role "-d" does not exist):
set -a && . ./.env && set +a
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" infra-db-1 \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\d goods"     # partial-unique на external_id, индекс на code
docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" infra-db-1 \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\d cells"     # UNIQUE(warehouse_id, address), type default 'storage'

make down && colima stop  # остановка
```

Проверено вживую (2026-07-21):
- **up → down → up** — все три `ok`; после отката остаётся только `schema_migrations`, после повторного наката — `version = 3, dirty = f`, все таблицы на месте.
- **Констрейнты (смоук):** два товара с `external_id = NULL` проходят; дубль одного GUID — отклонён (`goods_external_id_key`); дубль `(warehouse_id, address)` — отклонён; дубль `barcode` — отклонён; удаление товара каскадом уносит его ШК (сирот 0).
- **Статика:** `go build ./...` и `go vet ./...` — чисто (миграции встраиваются через `migrations/embed.go`).

> ⚠️ `make migrate-down` откатывает **все** миграции (раннер без шагов) — на dev это сносит и `users`; сид-админа возвращает `make seed`. На проде откат так не делают.
