# P2-02 · Локальная БД устройства: офлайн-стор и кэш справочников

**Статус:** готово (ветка `p2-02-offline-store`); проверено на живом DT50S с выключенным Wi-Fi.
**Фаза:** P2 (офлайн-ядро и синхронизация).

## Задача

Дать приложению работать без сети: справочники читаются из локальной базы устройства, а не из
API. Критерий — справочники доступны офлайн, репозитории читают из кэша.

## Решения

**Что кэшируем.** Товары, группы номенклатуры, поставщиков, ячейки и привязки штрихкодов —
то есть данные, которые меняет импорт из 1С и печать этикеток. События редкие и внешние по
отношению к работе кладовщика.

**Остатки НЕ кэшируем — они всегда идут в сеть.** Остаток меняется от каждой операции любого
терминала. Показать кладовщику число, которое уже неверно, хуже честного «нет связи»: по неверному
он примет решение. Раздел «Остатки» офлайн отдаёт список товаров из кэша, карточку остатков — нет.

**Поиск товаров перенесён в локальную базу.** Работает офлайн и мгновенно, попутно снимается долг
«поиск идёт seq-scan по `LIKE`». Плата — семантику пришлось повторить на клиенте: «все слова
присутствуют, порядок не важен», нижний регистр, «ё» → «е», поиск по названию, коду и полному
названию. Правила совпадают с серверными (P-FS-17), иначе кладовщик видел бы разные списки
в сети и без неё; совпадение закреплено тестами.

**Запись справочника — всегда полная замена в транзакции.** Сервер отдаёт справочник целиком,
и при слиянии удалённые на сервере записи жили бы в кэше вечно. Транзакция нужна, чтобы падение
посреди записи не оставило половину справочника: прежний кэш целиком лучше нового наполовину.

**Готовность считается по каждому справочнику отдельно, а не «все разом».** Изъян первой версии
вскрылся на устройстве: боевой сервер ответил 405 на новый эндпоинт выгрузки штрихкодов, и при
проверке «все или ничего» один недоступный справочник отключил бы офлайн целиком. Сейчас товары
и ячейки читаются из кэша, даже когда привязки ШК ещё недоступны.

**Публичная поверхность `CatalogRepository` не изменилась.** Сетевая реализация переехала в
`CatalogApi`, а под прежним именем остался фасад «сначала кэш». Ни один cubit и ни один виджет
править не пришлось.

## Что сделано

### Бэкенд

**`GET /api/v1/barcodes`** — выгрузка всех привязок ШК страницами, доступ `employee`, `total`
окном `COUNT(*) OVER()`, порядок по ШК стабилен. Без него привязки в кэш можно было бы собрать
только обходом всех товаров по одному запросу на каждый.

Новая модель `BarcodeLink` отличается от `Barcode` наличием `good_id`: там ШК перечисляются внутри
известного товара, здесь товар и есть то, что нужно узнать по коду.

### Клиент

- **`core/database/app_database.dart`** — база на drift: товары, группы, поставщики, ячейки,
  привязки ШК, отметки о синхронизации. Таблицы названы с префиксом `Cached`, потому что drift
  генерирует для таблицы `Goods` класс строки `Good` — ровно как доменная модель.
- **`features/stock/data/catalog_cache.dart`** — единственное место, где доменные модели
  превращаются в строки базы и обратно. Поля `searchText` у товара и `addressLower` у ячейки
  считаются при записи: нормализация нужна один раз на запись, а не на каждый запрос.
- **`features/stock/data/catalog_api.dart`** — сетевой источник (бывший `CatalogRepository`),
  плюс постраничная выгрузка всех товаров и всех привязок ШК.
- **`features/stock/data/catalog_repository.dart`** — фасад «сначала кэш».
- **`core/sync/catalog_sync_service.dart`** — наполнение кэша. Справочники укладываются по мере
  готовности, каждый в своей транзакции: обрыв связи посередине оставляет уже загруженное.
- Синхронизация запускается после входа (без ожидания) и вручную — пункт «Обновить справочники»
  в меню главного экрана, для случая «на портале только что загрузили номенклатуру».

## Проверка

```bash
cd apps/backend && go test ./... && golangci-lint run ./...
cd apps/craft_wms && flutter analyze && flutter test
flutter build apk --release -t lib/main.dart --dart-define-from-file=.env
```

Тестов **174** (было 144). Новые: 19 на кэш (семантика поиска, поддерево групп, замена вместо
слияния, экранирование `%` и `_`, готовность по каждому справочнику) и 12 на фасад (что из кэша,
что из сети, поведение без сети). На бэкенде — интеграционный тест выгрузки привязок
и постраничности.

**На живом DT50S с выключенным Wi-Fi:** список из 780 товаров открывается из кэша; поиск находит
товар и не делает ни одного сетевого запроса; «Ввод остатков» открывается без обращений к серверу
(раньше это были четыре запроса при каждом открытии).

Синхронизация после входа занимает около секунды на 780 товарах и 647 ячейках.

## Границы

Изменений схемы серверной БД нет — только новый эндпоинт чтения.

Осталось сделать:

- проверить офлайн-резолв по штрихкоду после выкатки `GET /barcodes` на прод: до неё сервер
  отвечает 405, и привязки в кэш не попадают;
- запись офлайн (привязка и отвязка ШК, ввод остатков) по-прежнему требует сети — это P2-03
  (очередь операций) и P2-04 (синхронизация очереди);
- индикатор офлайна и счётчик неотправленного — P2-07.
