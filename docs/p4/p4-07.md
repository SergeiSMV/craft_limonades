# P4-07 · Внутренний штрихкод для товара без ШК

**Статус:** ✅ завершена (gofmt/build/vet чисты, golangci-lint 0 issues, полный `go test ./...`
зелёный; 7 юнит-тестов символики и 5 интеграционных; цикл миграции up → down → up пройден;
сквозной смоук по живому стеку — выдача, повтор, резолв по коду, отказы).
**Категория:** плановая, фаза P4.

## Задача

Товары приезжают из 1С без штрихкода — на упаковке его просто нет. Такой товар выпадает из всей
работы склада: его не принять сканом, не найти в ячейке, не собрать в заказ. Нужно выдавать ему
свой код.

## Критерий готовности

Товар без ШК получает уникальный ШК, который читается ТСД как товар.

## Ключевые решения

### EAN-13 с префиксом 20–29 — и почему именно он

Решение заказчика (вопрос №4). Диапазон 20–29 зарезервирован GS1 под внутреннее использование:
производитель такой код выдать не может, значит столкновение с кодом из выгрузки 1С исключено
по построению, а не по везению.

Второй довод — **контрольная цифра живёт в самих данных**. Она ловит опечатку ручного набора,
а не только ошибку скана: переставленные местами соседние цифры ломают проверку. Code128, который
рассматривался как альтернатива, такого не умеет и остался у этикеток ячеек, где адрес
буквенно-цифровой.

Занят префикс `20`; остальные девять оставлены свободными на случай, когда понадобится отличать
разные виды внутренних кодов — например, весовые, где в теле лежит масса. Занимать весь диапазон
одним смыслом сейчас незачем.

### Принадлежность кода хранится флагом, а не разбирается из строки

`barcodes.is_internal` — тот же приём, что у `cells.is_default` и `internal_warehouses.is_default`.

Соблазн был определять «наш код» по префиксу: 20–29 ведь наш по договорённости. Но выгрузка 1С
может принести внутренний код **прежней системы** с тем же префиксом, и разбор строки выдал бы
его за наш. Проверка формы (`IsInternalEAN13`) в коде осталась, но она отвечает на вопрос «похож
ли», а не «наш ли», и это записано у неё в комментарии.

### Номера берутся из последовательности

`CREATE SEQUENCE internal_barcode_serial`. Выбор `max()+1` при двух одновременных генерациях
выдал бы один номер дважды, и вторая вставка упала бы на `UNIQUE(barcode)`. Последовательность
отдаёт номера без блокировок и переживает перезапуск.

Дыры в нумерации допустимы: откатившаяся транзакция свой номер не возвращает. Номер не документ
и не отчётная единица — непрерывность здесь ничего не стоит.

Потолок — десять цифр, ровно столько остаётся в EAN-13 после двузначного префикса и контрольной
цифры. На складских объёмах недостижим.

### Выдача идемпотентна по товару

Повторный вызов возвращает **тот же** код и сообщает `generated: false`. Иначе повторное нажатие
— связь мигнула, кладовщик не увидел ответа — дало бы товару два кода, из которых на упаковке
наклеен один, а второй жил бы в справочнике мусором. Перепечать испорченной этикетки идёт этим же
вызовом и даёт тот же код.

Отсюда и код ответа **200, а не 201**: вызов не обещает, что код создан именно сейчас. Что
произошло на самом деле, говорит поле `generated` — по нему экран решает, печатать молча или
сказать человеку, что он переклеивает существующий код.

### Выдача аддитивна

Товар может иметь и внешний ШК с упаковки, и наш: привязка 1→N, внутренний код встаёт рядом.
Это не противоречие — у коробки может быть свой штрихкод, а у штуки внутри нет.

### Занятый код не ломает выдачу

Если сгенерированный код уже лежит в справочнике как внешний (та самая выгрузка с чужим
внутренним кодом), берётся следующий номер — до пяти попыток. Повтор нужен не для подстраховки
от последовательности, она уникальна, а именно для этого случая.

### Символика вынесена в отдельный пакет

`internal/barcode` — чистая арифметика, без БД, HTTP и складских понятий. Её удобно проверять
таблицей известных кодов, и она понадобится не только генерации: печать товарного ярлыка (`P4-08`)
обязана проверить код перед выводом на этикетку.

Контрольная цифра проверяется на **реальных кодах** — пример из спецификации GS1, настоящий код
товара, ISBN-13 (та же схема), — а не на собственных вычислениях. Иначе тест подтверждал бы
реализацию самой собой.

## Границы задачи

Печать товарного ярлыка с этим кодом — `P4-08`; там же впервые понадобится кириллица в тексте
этикетки (наименование товара), и шрифт `5` для неё брать нельзя (`P4-06`).

Экран, с которого кладовщик выдаёт код товару, — `P4-09`: здесь готов API, вызывать его из потока
приёмки будет он же.

Выдача идёт прямой ручкой, не через очередь операций: типов `barcode_internal_*` в `POST
/operations` нет. Осталось сделать: решить вместе с `P4-09`, нужна ли выдача офлайн. Повод
сомневаться есть — код должен быть уникален в системе, а офлайн-генерация этого обещать не может
без диапазонов номеров, выданных терминалу заранее.
