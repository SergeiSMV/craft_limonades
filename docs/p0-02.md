# P0-02 · Go-скелет сервиса

**Статус:** ✅ завершена (проверено локально и в стеке)
**Задача:** Go-скелет: chi/echo, конфиг из env, логгер, graceful shutdown, `/health`.
**Критерий готовности:** сервис стартует, читает конфиг из окружения, пишет логи и отвечает 200 на `/health`; при остановке гасится корректно.

Общая архитектура проекта — в [architecture.md](architecture.md).

---

## Что сделано

| Артефакт                                              | Назначение                                                                        |
|-------------------------------------------------------|-----------------------------------------------------------------------------------|
| `apps/backend/cmd/server/main.go`                     | Точка входа: сборка конфига, логгера, сервера; graceful shutdown по сигналам ОС   |
| `apps/backend/internal/config/config.go`              | Загрузка настроек из env (`APP_PORT`, `LOG_LEVEL`) с дефолтами                    |
| `apps/backend/internal/handler/health.go`             | Обработчик `/health` → 200 JSON `{"status":"ok"}`                                 |
| `apps/backend/internal/handler/router.go`             | Сборка chi-роутера: middleware + маршруты (транспортный слой)                     |
| `apps/backend/internal/middleware/logger.go`          | Middleware структурного логирования HTTP-запросов через slog                      |
| `apps/backend/go.mod` / `go.sum`                      | Зависимость `go-chi/chi/v5 v5.3.1`                                                |
| `.env` / `.env.example`, `infra/docker-compose.yml`   | Проброс `LOG_LEVEL` в окружение сервиса                                           |

### Ключевые решения

- **Роутер — chi** (не echo): лёгкий, ближе к стандартной библиотеке; это скелет для всех будущих API-ручек.
- **Логгер — slog** (стандартная библиотека), JSON в stdout — стандарт для контейнеров; уровень задаётся `LOG_LEVEL`.
- **Слои по чистой архитектуре:** `config` (настройки) → `handler` (транспорт: health + router) → `middleware` (общие обёртки). Бизнес-логики нет — это «розетка».
- **Graceful shutdown:** по SIGINT/SIGTERM сервер перестаёт принимать новые соединения и даёт текущим запросам до-обработаться в пределах таймаута (10 с), затем выходит. Зачем: не рвать операцию на полуслове — в WMS это критично для консистентности остатков.
- **`ReadHeaderTimeout`** у сервера — защита от медленных клиентов (Slowloris).
- **`/health` пока без проверки БД** — простой liveness; ping БД добавится в P0-03, когда появится подключение.

## Запуск и проверка критериев готовности

### 1. Сборка и статический анализ

```bash
cd apps/backend
go vet ./... && go build ./...
```
Ожидаемо: без ошибок.

### 2. Конфиг из env + `/health` (локально, вне docker)

```bash
cd apps/backend
go build -o /tmp/craftwms ./cmd/server
APP_PORT=18080 LOG_LEVEL=debug /tmp/craftwms &
sleep 0.5     # дать сервису забиндить порт (иначе curl может успеть раньше → HTTP 000)
curl -s -w "\nHTTP %{http_code}\n" http://localhost:18080/health
```
Ожидаемо: `{"status":"ok"}`, `HTTP 200`. В логах старта — `"addr":":18080"`, `"log_level":"DEBUG"` (значения прочитаны из env).

> Если `curl` вернул `HTTP 000` — это либо гонка (запустился раньше сервера — помогает `sleep` выше),
> либо в шелле задан `http_proxy` (тогда добавить `curl --noproxy '*' ...`). Проверить: `echo "$http_proxy"`.

### 3. Структурные логи запросов

Каждый запрос логируется строкой JSON с уровнем и полями:
```json
{"level":"INFO","msg":"http request","method":"GET","path":"/health","status":200,"duration_ms":0,"request_id":"...","remote":"..."}
```

### 4. Graceful shutdown (главная часть критерия)

```bash
kill -TERM %1     # послать SIGTERM запущенному сервису
```
Ожидаемо в логах и exit code:
```
{"level":"INFO","msg":"shutdown signal received, draining connections"}
{"level":"INFO","msg":"server stopped cleanly"}
# процесс завершается с кодом 0
```

### 5. В составе стека — `/health` через nginx

Выполнять **из корня проекта** (там лежит `Makefile`):

```bash
cd <корень проекта>                       # напр. из apps/backend: cd ../..
make up
make ps                                   # все контейнеры healthy
curl -s -w "\nHTTP %{http_code}\n" http://localhost:8080/health
```
Ожидаемо: три контейнера `healthy`; ответ `{"status":"ok"}`, `HTTP 200` (через nginx). Логи бэкенда: `docker logs infra-backend-1`.

Остановка (из корня проекта):

```bash
make down       # остановить и удалить контейнеры (данные БД сохранятся в volume infra_db_data)
colima stop     # остановить сам docker-демон, когда работа закончена совсем
```
Подробнее про варианты остановки (пауза без удаления, удаление с volume) — в [p0-01.md](p0-01.md).

## Границы задачи

- Бизнес-логики нет — только каркас. Auth, справочники и операции подключаются позже.
- Подключения к PostgreSQL пока нет: `DATABASE_URL` уже прокинут в окружение контейнера, но сервис его не использует. БД (pgx/sqlx) + миграции — задача **P0-03**.
- `/health` — простой liveness; проверка доступности БД добавится в P0-03.
