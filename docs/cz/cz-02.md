# CZ-02 · Подписант и клиент True API

**Статус:** ✅ завершена (проверено на проде: подпись, токен, чтение марки и короба, отказ при остановленном подписанте).

## Задача

Научить бэкенд самому получать токен True API и читать по нему данные марок, без ручных
действий: подписать строку `auth/key` КЭП, обменять её на токен, держать токен в памяти и
обновлять до истечения. Если подписант недоступен, вернуть понятную ошибку, а не таймаут.

## Критерий готовности

Бэкенд на проде сам получает токен и читает марку через True API:
`POST /api/v1/admin/cz/info` с КИ реальной марки отдаёт данные продукции. Повторный вызов
не подписывает заново. После рестарта бэкенда токен получается без участия человека.
При остановленном подписанте `GET /api/v1/admin/cz/status` отвечает «подписант недоступен».

## Устройство

```
хост: cz-signer.service (User=$CZ_SIGNER_USER, Group=cz-signer)
  ├─ cryptcp → контейнер \\.\HDIMAGE\cz-signer (файловая копия ключа)
  └─ /run/cz-signer/sign.sock  (0660, группа cz-signer)
            │  том, только этот каталог
backend-контейнер (group_add: gid cz-signer)
  └─ trueapi.Client → https://markirovka.crpt.ru/api/v3/true-api
```

- **Подписант — служба systemd на хосте, а не контейнер.** КриптоПро CSP, ключ, сертификат
  в `uMy` и лицензия уже стоят на сервере (CZ-01). Контейнер потребовал бы второй установки
  CSP: дистрибутив распространять нельзя, поэтому образ пришлось бы собирать на сервере мимо
  CI, а лицензию заводить заново. Требования плана сохраняются: подписант в сеть не выходит,
  ключ не попадает в бэкапы.
- **Связь — unix-сокет.** Каталог `/run/cz-signer` монтируется в контейнер бэкенда. Права
  на сокет даёт группа `cz-signer`, бэкенд входит в неё через `group_add`. TCP-порта нет
  совсем: ни наружу, ни в сеть compose.
- **Бинарь подписанта — на Go, едет в образе бэкенда** (`/usr/local/bin/cz-signer`, сборка
  без CGO, как у остальных). `update.sh` достаёт его через `docker cp`, так же как бандл
  портала, кладёт в `/opt/craft-wms/bin/` и перезапускает службу, если бинарь изменился.
  Подписант обновляется вместе с релизом, отдельной доставки нет.
- **Подписант ничего не знает о True API.** Он умеет одно: подписать присланные байты
  присоединённой подписью CAdES-BES (`cryptcp -sign -cadesbes -attached -der`) и вернуть
  подпись. Получение токена, кэш и обновление живут в бэкенде.
- **Пароль копии ключа — не в `.env.prod`.** Он лежит в `/opt/craft-wms/cz-signer.env`
  (`root`, `600`), его читает systemd через `EnvironmentFile`. Бэкенд пароля не видит.
  Пароль уходит в `cryptcp` аргументом `-pin` на время одного вызова, раз в несколько часов.

## План реализации

1. ✅ **Подписант `cmd/cz-signer`** (пакет `internal/czsigner`, бинарь в образе бэкенда).
   HTTP поверх unix-сокета:
   - `POST /sign` — тело: байты для подписи, ответ: подпись DER;
   - `GET /health` — сертификат с заданным отпечатком найден и ключ доступен (пробная подпись).

   Настройки из окружения: путь сокета, отпечаток (`CZ_SIGNER_THUMB`), пароль
   (`CZ_SIGNER_PIN`), путь к `cryptcp`. Каждая подпись — во временном каталоге с правами
   `700`, удаляется сразу. Таймаут на вызов, один вызов за раз. Тесты гоняют подставной
   `cryptcp`-скрипт. Сокет от прошлого запуска служба удаляет сама, а обычный файл на его
   месте не трогает. Права на сокет — `660`.
2. ✅ **Клиент `internal/trueapi`**, данные марки и ошибки-сигналы — в `model/cz.go`.
   - `Signer` — интерфейс, реализация ходит в сокет.
   - Получение токена: `GET /auth/key` → подпись → `POST /auth/simpleSignIn`.
   - Кэш в памяти. Срок берётся из `exp` токена; токен обновляется заранее, за час до
     истечения. Параллельные запросы ждут одно обновление и не подписывают каждый своё.
     Если обновить не вышло, а старый токен годен ещё больше минуты, работаем на старом.
     На `401` клиент сбрасывает токен и повторяет запрос один раз.
   - Фоновое обновление по таймеру: первый запрос с ТСД не ждёт подписи, а сбой виден
     сразу, ошибкой в Bugsink, а не на складе. После неудачи пауза растёт вдвое: от 1 до
     15 минут.
   - `CisesInfo(ctx, codes)` — `POST /cises/info`. Модель берёт нужные WMS поля, ответ ЧЗ
     по коду целиком хранится в `Raw`. Поля сверены с живым ответом на проде (марка пива и
     её транспортный короб): вид упаковки — `generalPackageType` (`UNIT`, `BOX`), а
     `packageType` — уровень (`UNIT`, `LEVEL1`); он идёт отдельным полем `package_level`.
   - Ошибки-сигналы в `model`: подписант недоступен, нет договора по товарной группе (`403`),
     марка не найдена (`404`), True API недоступен. Тесты — на `httptest` и подставном
     подписанте.
3. ✅ **Сервис и ручки admin** (`service/cz.go`, `handler/cz.go`, настройки `CZ_SIGNER_SOCKET`,
   `CZ_API_URL`, `CZ_TOKEN_REFRESH_BEFORE`).
   - `GET /api/v1/admin/cz/status` — подписант жив (пробная подпись), токен есть, когда
     истекает. Всегда `200`: «не настроено» — это ответ, а не сбой.
   - `POST /api/v1/admin/cz/info {codes}` — данные марок, до 100 кодов за раз. Криптохвост
     после GS сервис отрезает сам: коды можно давать прямо со сканера. Ответы: `400` — нет
     кодов; `503` — не настроено или подписант недоступен; `502` — ЧЗ отказал во входе или
     True API недоступен; `422` — нет договора по группе; `404` — код не найден. Сбои `5xx`
     уходят в Bugsink.

   Нужны для проверки и для панели; складские сценарии придут в CZ-03…CZ-05. Без
   `CZ_SIGNER_SOCKET` клиент выключен, а ручки отвечают «Честный знак не настроен».
   Локальный стек и тестовый стенд работают как раньше.
4. ✅ **Деплой.**
   - Юнит `deploy/systemd/craft-wms-cz-signer.service`. Ставится, только если в `.env.prod`
     задан `CZ_SIGNER_USER`. Пока нет `cz-signer.env` или бинаря, служба не стартует — по
     `ConditionPathExists`, без ошибки. Каталог сокета — `RuntimeDirectory` с
     `RuntimeDirectoryPreserve=yes`: он смонтирован в контейнер и при перезапуске службы
     должен остаться тем же. Юнит переписывается и служба перезапускается, только если
     содержимое изменилось: `update.sh` зовёт установку каждые 5 минут.
   - Группа `cz-signer` заводится сама, её GID пишется в `.env.prod` (`CZ_SIGNER_GID`),
     только если изменился. В `install.sh` — до `up -d`.
   - Бинарь — `/opt/craft-wms/bin/cz-signer`. `update.sh` (шаг 3a) и `install.sh` достают
     его из образа бэкенда; одинаковый не трогают, новый подменяют через `mv` и
     перезапускают службу. Неудача — обновление неполное, работающий подписант остаётся.
   - В `infra/docker-compose.prod.yml` у бэкенда: `CZ_SIGNER_SOCKET`, `CZ_API_URL`,
     `CZ_TOKEN_REFRESH_BEFORE`, `group_add` с GID (без подписанта — `nogroup`), том
     `/run/cz-signer` только на чтение — в сокет писать это не мешает.
   - В гейте `ci-deploy.yml` проверка `ExecStart` смотрит только пути внутри репозитория:
     у подписанта там бинарь вне клона.
5. ✅ **Панель `craft.sh`**, скрипт `deploy/cz-setup.sh`.
   - Пункт 18 «Настроить подписант»:
     - спрашивает пользователя с ключом и показывает его сертификаты в `uMy`;
     - спрашивает отпечаток (сверяет с хранилищем) и пароль копии;
     - пишет `cz-signer.env` (root, `600`; пароль — в одинарных кавычках, чтобы systemd взял
       его как есть), а в `.env.prod` — `CZ_SIGNER_USER` и `CZ_SIGNER_SOCKET`;
     - ставит юнит, группу и бинарь, перезапускает службу и backend и проверяет. Backend
       перезапускается всегда: иначе после неудачных входов (неверный пароль копии) он ждал
       бы повтора до 15 минут.
   - Пункт 19 «Проверить ЧЗ» входит админом один раз за запуск (у входа лимит 10 в минуту)
     и идёт по звеньям:
     - служба работает;
     - пробная подпись прямо через сокет;
     - бэкенд получил токен — ожидание до полутора минут, чтобы перекрыть минутный повтор
       входа;
     - по желанию — чтение марки по введённому КИ.
   - В чек-листе (пункт 5) — работает ли подписант и срок лицензии КриптоПро.
   - `admin_token` переехал из `monitoring-setup.sh` в `_lib.sh` — им пользуются оба скрипта.
6. ✅ **Проверка на проде.**
   - Пункт 18: подписант настроен, пробная подпись прошла. Первый запуск был с неверным
     паролем копии — КриптоПро ответил `0x8010006B` (wrong PIN), бэкенд записал сбой входа
     ошибкой; со вторым запуском бэкенд получил токен сам, на очередной попытке, на 10 часов.
   - Пункт 19: транспортный короб пива (`00`+SSCC) — группа, статус, владелец, 24 марки в
     `child`; марка из него — наименование, GTIN, даты производства и годности, `parent` —
     тот же короб. По живому ответу исправил поле вида упаковки (`generalPackageType`).
   - Подписант остановлен — пункт 19 сразу отвечает «служба … не работает», без таймаута.
   - Рестарт бэкенда новым образом (выкатка правки) — токен получен сам за доли секунды
     после старта; короб отдаётся как `BOX`, уровень `LEVEL1`, 24 марки.
   - Найдено и исправлено по ходу: проверка входила админом на каждом опросе и упиралась в
     лимит входов (429); повторная настройка не перезапускала бэкенд.
   Скрипты `scripts/cz-probe/` остаются для ручной разведки.
7. ✅ **Документы.** Этот файл, `docs/cz/README.md`, `docs/architecture.md` (подписант и
   клиент), `docs/deploy/prod-deploy.md` (настройка подписанта), ADR-0017 (раздел
   «Последствия» для CZ-02 — где живёт ключ).

## Проверка

Локально, без КриптоПро и сети — подставной `cryptcp` и фальшивый True API:

```bash
cd apps/backend
go test -race ./internal/czsigner ./internal/trueapi
go test -run CZ ./internal/service ./internal/handler
```

Ожидаемо: `ok` по всем пакетам.

На проде, после выкатки:

```bash
sudo bash /opt/craft-wms/app/deploy/cz-setup.sh          # пункт 18: настройка + проверка
sudo bash /opt/craft-wms/app/deploy/cz-setup.sh --test   # пункт 19: только проверка
```

Ожидаемо: «Подписант подписывает», «Токен получен, действует до …», по введённому КИ — товар,
группа, упаковка, статус и даты.

Подписант остановлен — понятный отказ, а не таймаут:

```bash
sudo systemctl stop craft-wms-cz-signer
sudo bash /opt/craft-wms/app/deploy/cz-setup.sh --test   # «служба … не работает»
sudo systemctl start craft-wms-cz-signer
```

## Границы задачи

- Складских сценариев с марками нет — они в CZ-03…CZ-05.
- Постоянная лицензия КриптоПро CSP не покупается в этой задаче: пробная действует до
  ~2027-01-24.
