# CZ-05 · Приёмка маркированного товара: марки в короб и ячейку

**Статус:** ✅ готово.

## Задача

Принимать маркированный товар по маркам Честного знака: транспортный короб ЧЗ — одним сканом с
составом, марки россыпью — по одной в свой короб или в ячейку. Каждая принятая марка
привязывается к товару, партии, коробу и ячейке. Расхождения с ЧЗ попадают в «Проблемы склада».

## Критерий готовности

Приёмка маркированного товара привязывает каждую марку к коробу и ячейке: после проводки
`cz_marks` знает по каждой марке товар, партию и место, короб ЧЗ — это ГЕ с составом; марка
с чужим владельцем или выбывшая — на остатке «Изолятора» с открытой проблемой склада.

## Устройство

Решения (2026-10-23):

- **Какой товар маркируемый (долг 16) — по факту, с ручной правкой.** У товара флаг
  `cz_marked`. Ставится сам: при привязке ШК из марки (скан марки → привязка, CZ-04) и при
  приёме марки товара. Правит его переключателем в карточке товара на ТСД только admin;
  кладовщик видит признак без правки. Колонки «маркируемый» в выгрузке 1С нет — импорт флаг не
  трогает. На приёмке маркируемый товар по ШК не принимается: «сканируйте марку».
- **Марки — только со связью (долг 17).** Скан марки или короба на приёмке сразу читается из ЧЗ
  (`cz/scan`, CZ-04): кладовщик видит состав и расхождения на месте. Без связи немаркируемый
  товар принимается как раньше, маркируемый ждёт связи. Отправка приёмки — по-прежнему очередью
  `receipt_submit`: данные ЧЗ к моменту отправки уже прочитаны.
- **Короб ЧЗ — ГЕ без ярлыка.** Скан `00`+SSCC заводит в приёмке короб с id устройства и кодом ЧЗ;
  строки короба — из состава ЧЗ (товар по GTIN, партия — дата производства единицы, количество —
  число марок). Кладовщик выбирает только ячейку. Групповые упаковки внутри — агрегаты с
  `parent_code`.
- **Марка россыпью** добавляет единицу в строку текущего короба (свой короб с QR) или россыпи:
  товар и партия — из ЧЗ, без диалога даты и количества. Повторный скан той же марки — «уже
  отсканирована». Групповая упаковка — как набор марок своего состава.
- **Незнакомый GTIN — привязка ШК поиском** (CZ-04); привязка из марки ставит товару
  `cz_marked`.
- **Расхождения — принять и сразу в проблемы.** Сервер при скане отмечает расхождение: владелец
  марки — не наша организация (ИНН — настройка `CZ_OWNER_INN`, её спрашивает пункт 18 панели;
  имени поля ИНН в токене True API мы не знаем, а гадать нельзя), марка не в обороте
  (`status` ≠ `INTRODUCED`). ТСД показывает строку с пометкой. При проводке сервер в той же
  транзакции заводит «Проблему склада»: короб ЧЗ с расхождением — на ГЕ целиком, марки россыпью —
  на товар и партию с их числом; товар уходит в «Изолятор», дальше решает офис, как сейчас.
  Причины: «чужая марка» (`foreign_mark`, есть) и новая «выбыла из оборота» (`retired`; решения —
  списать или вернуть поставщику).
- **«Не тот товар»** на приёмке не возникает: ожидаемого состава у приёмки нет, а незнакомый GTIN
  привязывается к товару. Остаётся для отгрузки (CZ-07).
- **Ошибки ЧЗ при проводке — отказ, а не повтор:** «марка уже принята», «короб уже принят»
  (`ErrCZMarkExists`, `ErrCZAggregateExists`) — в список отказов операции; иначе очередь ТСД
  повторяла бы её бесконечно.

## План реализации

1. ✅ **Миграция `000027_cz_receipt`:**
   - `goods.cz_marked boolean NOT NULL DEFAULT false`;
   - причина проблемы `retired` (CHECK; решения по ней — в коде, шаг 2);
   - связь марки с проблемой — `cz_marks.problem_id` (какие марки ушли в «Изолятор»).

   Откат превращает проблемы `retired` в «прочее» с пояснением в комментарии: удалить их
   нельзя — за ними остаток в «Изоляторе». Проверено на копии снимка прода: 22 → 27, проблема
   `retired` вставляется, чужая причина отвергается, откат с живой проблемой и повторный подъём.
2. ✅ **Сервер, справочник и скан:**
   - `cz_marked` в ответе товаров, карточке товара и поиске товара по ШК;
   - `PATCH /api/v1/goods/{id}/cz-marked {cz_marked}` — только admin (`CZService`, не старый
     `CatalogService`: новый код — по слоям);
   - `bind_barcode` с `from_cz_mark: true` ставит флаг в той же транзакции, что и привязку;
     старые клиенты поле не шлют;
   - причина `retired`: решения — списать или вернуть поставщику (разместить обратно — нет:
     выбывшую марку продать нельзя);
   - `cz/scan` отдаёт `discrepancy` (`foreign_mark` / `retired`) у кода и у строки состава;
     единицы с расхождением — отдельной строкой. Пустой `CZ_OWNER_INN` — владелец не
     сверяется (в журнал — предупреждение); `CZ_OWNER_INN` — в compose, шаблоне `.env.prod`
     и пункте 18 панели.
3. ✅ **Сервер, `receipt_submit`:**
   - тело расширено необязательными полями, старые клиенты их не шлют: у ГЕ — `cz_code`
     (`00`+SSCC: ГЕ — короб ЧЗ, id ей выдало устройство), список `cz_groups` (`code`,
     `parent_code`), у строки — `marks` (`cis`, `aggregate_code`, `discrepancy`); партия марки —
     `production_date` строки;
   - сервис до базы проверяет форму (`service/operations_receipt_cz.go`): коды по виду,
     упаковка вложена только в упаковку той же приёмки и без циклов, марка без повторов, марка
     короба ЧЗ — в строке этого короба, расхождение из списка, марок не больше количества строки;
   - проводка (`repository/receipt_cz.go`, `receiveCZ`) — после `postReceipt`, в той же
     транзакции: агрегаты (родитель раньше вложенной), проверка, что GTIN марки — ШК товара
     строки, марки с местом (в коробе — ГЕ, россыпью — ячейка строки и склад по умолчанию),
     флаг `cz_marked` товарам;
   - расхождения: короб ЧЗ, где есть хоть одна такая марка, уходит в «Изолятор» целиком (одна
     ГЕ — одна метка склада), причина — «чужая марка», если такая в нём есть, иначе «выбыла»;
     `mark` проблемы — код короба, `problem_id` — у всех его марок. Марки россыпью и в своём
     коробе с QR — проблема на товар и партию строки с их числом, отдельная на причину; из
     своего короба товар вынимается в россыпь «Изолятора» той же ячейки, марки — за ним.
     Проблема из приёмки минует только запрет ячейки приёмки (`fromReceipt`), автор — автор
     приёмки, склад — «Изолятор» по коду `ISOLATOR`;
   - изолированная россыпь в ячейке приёмки убирается из задания на размещение
     (`excludeFromPutawayTask`): размещение берёт россыпь только «Основного», и позиция не
     закрылась бы никогда; опустевшее задание удаляется. Короб «Изолятора» в задании остаётся —
     метка склада переезжает с ним;
   - отказ, а не повтор: `ErrCZMarkExists`, `ErrCZAggregateExists`, `ErrCZBadCode`,
     `ErrCZUnknownGTIN` и новые `ErrCZMarkGoodMismatch`, `ErrCZMarksExceedQty` — в `isRejection`;
   - эталон `testdata/receipt_submit_cz.json` (короб ЧЗ с упаковкой и марки россыпью, одна
     чужая), Go-тесты `handler/receiving_cz_http_test.go` (эталон, короб с выбывшей маркой,
     изолированная россыпь без задания, отказы) и `service/operations_receipt_cz_test.go`
     (проверки формы). Весь бэкенд с Docker и lint — зелёные.
4. ✅ **ТСД, справочник:**
   - `cz_marked` в модели товара и кэше (база ТСД **10**): подъём 9 → 10 добавляет колонку
     и снимает отметку загрузки товаров — до следующей синхронизации справочник читается с
     сервера, иначе маркируемый товар выглядел бы немаркируемым;
   - привязка ШК из марки (скан марки незнакомого GTIN) шлёт `from_cz_mark: true`; следствие
     операции в очереди сразу помечает товар в кэше, карточка открывается уже с признаком;
   - блок «Маркировка ЧЗ» в карточке товара (`cz/presentation/widgets/cz_marked_section.dart`)
     видят все, admin правит выбором «Маркируемый / Без марки»: `PATCH goods/{id}/cz-marked`
     только онлайн, кэш — после ответа сервера; новый код по слоям — `CzGoodRepository`
     (domain), `CzGoodRepositoryImpl` (data), `CzMarkedCubit`;
   - причина `retired` («Марка выбыла из оборота») — в `ProblemReason` и подписях ТСД и портала;
     кладовщику на выбор при пометке она не предлагается (`selectable: false`): ставит её
     только приёмка по ответу ЧЗ;
   - тесты: `test/features/cz/cz_marked_test.dart` (кэш, правка admin, без связи, привязка из
     марки, миграция 9 → 10); весь набор Flutter и `flutter analyze` — зелёные.
5. ✅ **ТСД, приёмка:**
   - ответ `cz/scan` дополнен (сервер): `groups` — групповые упаковки внутри с вложенностью и
     `parents` — КИ единицы → её упаковка. Упаковка определяется по тому, чьим ребёнком код
     пришёл при раскрытии, а не по полю `parent` ЧЗ: ссылка всегда ведёт на код, известный
     приёмке; вложенный короб (короб в паллете) упаковкой не считается. Эталоны
     `cz_scan_*.json` дополнены;
   - на ТСД ответ разбирает `discrepancy`, `groups`, `parents`; скан марки и короба ЧЗ на
     приёмке — миксин `ReceiptCzScanActions`, только онлайн («нужна связь»);
   - короб ЧЗ — новая ГЕ в текущей ячейке с кодом `00`+SSCC (id выдаёт терминал), строки —
     состав по товару и партии, марки с упаковкой; закрыт: в него не добавляют ни марки, ни
     товар, его строки не правят и не удаляют (короб уходит целиком), ярлык не печатается,
     в списке и шапке — «Короб ЧЗ» с хвостом SSCC. Повторный скан короба этой приёмки
     открывает его; короб, уже принятый на склад, — отказ;
   - марка или групповая упаковка — единицами в текущий короб с QR или россыпью, товар и
     партия из ЧЗ, без диалога даты и количества; повтор марки — «уже есть в приёмке», марка,
     числящаяся на складе, — отказ; строку с марками не правят;
   - незнакомый GTIN — привязка ШК (EAN-13 из GTIN) к выбранному товару с `from_cz_mark`;
   - маркируемый товар по ШК и вручную не принимается: «сканируйте марку»;
   - строка показывает число марок и, красным, расхождения с ЧЗ («в «Изолятор»»);
   - черновик хранит код короба ЧЗ, марки строк и упаковки — переживает перезапуск;
   - тело `receipt_submit`: `cz_code` у ГЕ, `cz_groups`, `marks` у строки — только когда
     они есть, приёмка без марок уходит прежним телом;
   - логика марок без состояния — `receipt/presentation/bloc/receipt_cz.dart`; тесты —
     `receipt_cz_test.dart` (разбор скана, короб, россыпь, повторы, черновик) и
     `receipt_cz_wire_contract_test.dart` на эталон `receipt_submit_cz.json`. Весь набор
     Flutter, `flutter analyze`, весь бэкенд с Docker и lint — зелёные.
6. ✅ **Проверка на стенде** (снимок прода от 21.10, 780 товаров):
   - `stand.sh migrate` поверх базы стенда: схема 26 → 27, `/ready` отвечает; у всех товаров
     `cz_marked` — «нет» (признак по факту, задним числом не ставится);
   - сквозной прогон — на копии базы стенда, чтобы не засорять её: бэкенд ветки, вход по

     ячейку хранения и марок россыпью в ячейку приёмки (одна чужая), приёмка короба ЧЗ с
     выбывшей маркой, повтор принятой марки. Итог: обе приёмки проведены, повтор отклонён
     («mark already exists»), товар помечен маркируемым; марки — в коробах и россыпью на своих
     местах, упаковка — в своём коробе, чужая марка и короб с выбывшей — в «Изоляторе» с
     открытыми проблемами (`mark` — КИ и код короба), офису по «выбыла» предложены «списать» и
     «вернуть поставщику»; в задании на размещение — «Основная» россыпь и короб; документы
     «Поступление» созданы;
   - откат 27 на той же копии с живой проблемой `retired` (down → up в одной транзакции):
     проблема становится «прочее» с пояснением, колонки уходят, подъём возвращает схему и
     причина `retired` снова принимается;
   - копия удалена, стенд и Colima остановлены.

## Границы задачи

- Марки в размещении, перемещении и отгрузке, вскрытие короба — CZ-06; Excel отгрузки — CZ-07.
- Без связи марки не принимаются — решение по долгу 17.
- Первая приёмка нового маркируемого товара, который ни разу не сканировали маркой, пройдёт по ШК
  без марок — ограничение решения по долгу 16.
- Снять ошибочно отсканированную марку по одной нельзя — только строку россыпи целиком или
  короб ЧЗ целиком.
- На проде (PR #230/#231): ИНН организации `6234203222` введён пунктом 18 панели `craft.sh`
  (`CZ_OWNER_INN`) — владелец марки сверяется.
