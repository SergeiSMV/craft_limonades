# P-FS-17 · Поиск по словам, фильтры и привязка ШК из карточки

**Статус:** готово (ветка `p-fs-17-stock-search-ux`); ✅ проверено на DT50 вживую.
**Фаза:** P-FastStart (доводка раздела «Остатки», после P-FS-15/16).

## Задача

Три независимых пункта по разделу «Остатки» плюс одно расследование:

1. Поиск по наименованию не находил товар, если слова стоят в другом порядке или не подряд:
   «фома бекон» не находило «Арахис в хрустящей корочке Бекон (ТМ Фома Лукич)».
2. Выпадающие списки фильтров (группа/поставщик) — привести к стилю приложения; длинные
   названия не обрезать.
3. Привязать штрихкод к товару прямо из карточки остатков.
4. Выяснить, почему при переходе в карточку товара уходит запрос на список товаров.

## Критерий готовности

Поиск находит товар при любом порядке слов и по незаконченному слову; поиск по скану ШК не
сломан; `flutter analyze` без замечаний, тесты и релизная APK зелёные; на бэкенде `go vet`,
golangci-lint и полный `go test ./...` зелёные.

## 1. Поиск товаров по словам

### Причина

Вся поисковая строка уходила в один `ILIKE '%…%'` по `name` **или** `code`
(`internal/repository/catalog_read.go`). Совпадение требовалось непрерывной подстрокой, поэтому
многословный запрос не находил ничего, а `full_name` (развёрнутое наименование из 1С)
в поиске не участвовал вовсе.

### Решение

Поиск «все слова присутствуют, порядок не важен»: строка бьётся на слова, каждое должно
встретиться в товаре. Слова уезжают в БД одним параметром `text[]` — динамический SQL не нужен.

**Сервис (`internal/service/catalog.go`)**

- **`searchWords(query)`** — `strings.Fields` + нормализация каждого слова, потолок
  `maxSearchWords = 10` (каждое слово — отдельный `LIKE` по каждой строке).
- **`normalizeSearch`** — нижний регистр и **«ё»→«е»**: кладовщик набирает «береза», в 1С
  «Берёза». Обе стороны сравнения нормализуются одинаково.
- **`likeEscaper`** — экранирует `\`, `%`, `_`. Найдено попутно: до этого ввод «50%» искал «50»
  и любой хвост, а «_» совпадал с любым символом.

**Репозиторий (`internal/repository/catalog_read.go`)**

`GoodsFilter.Query string` → `Words []string`; предикат:

```sql
WHERE (cardinality($1::text[]) = 0 OR NOT EXISTS (
        SELECT 1 FROM unnest($1::text[]) AS w
        WHERE replace(lower(g.name || ' ' || coalesce(g.code, '') || ' ' || coalesce(g.full_name, '')), 'ё', 'е')
              NOT LIKE '%' || w || '%'
      ))
```

`NOT EXISTS` отсекает товар, у которого хоть одно слово не нашлось. Ищем по склейке
**name + code + full_name**. Пустой массив = фильтр не применяется. Клиент не изменялся:
`GET /goods?q=` и формат ответа прежние.

### Поиск по скану ШК не задет (проверено)

Он идёт мимо этого запроса: клиент распознаёт скан (`looksLikeBarcode`) и дёргает отдельный
`GET /api/v1/barcodes/{code}`, а `ListGoods` по штрихкодам никогда и не искал. Все тесты ШК
(`barcode_integration_test.go`) зелёные.

### Отвергнутые варианты

- **Полнотекстовый поиск (`tsvector` + словарь `russian`)** — дал бы стемминг и ранжирование,
  но требует миграции с generated-колонкой и GIN-индексом, а главное ломает поиск по мере ввода:
  «бек» перестал бы находиться без префиксных `:*`-запросов. На ТСД кладовщик набирает 3–4 буквы,
  это шаг назад.
- **`pg_trgm` + `similarity` (опечатки)** — нужен подбор порога, на коротких запросах ведёт себя
  непредсказуемо. Возвращаться, если попросят «искать с опечатками».
- **Ранжирование выдачи** не вводили — сортировка прежняя, `ORDER BY g.name`.

⚠ **Производительность.** `LIKE '%…%'` индекс не использует — это seq scan. На текущем каталоге
(сотни позиций) неважно. При росте до десятков тысяч лечится одной миграцией: расширение
`pg_trgm` + `GIN (… gin_trgm_ops)`, который ускоряет именно `LIKE '%…%'`. Занесено в
`dev-context.md` §9.

## 2. Нижний лист фильтров

Два одинаковых дропдауна свёрнуты в общий `_FilterDropdown` (было ~90 строк копипасты на группу
и поставщика).

- **Каждый вариант меню — `NeumorphicButton`.** Тап обрабатывает сама кнопка: её
  `GestureDetector` перехватывает жест раньше `DropdownMenuItem`, и штатный `onChanged`
  не сработал бы. При `onPressed: null` было бы хуже — тап всё равно съедается, а `_getDepth()`
  возвращает 0 и плашка становится плоской.
- **Контекст для закрытия меню — от пункта, через `Builder`.** Список `items` строится в `build`
  листа; с этим контекстом `Navigator.pop` закрыл бы **весь нижний лист**, а не выпадающее меню.
- **Длинные названия переносятся на следующую строку:** снят `overflow: ellipsis`, у дропдауна
  `itemHeight: null` — иначе пункт жёстко ограничен 48 px и второй строке некуда деться.
- **`selectedItemBuilder`** — в свёрнутом поле обычный текст в одну строку: иначе внутри поля
  рисовалась бы вторая неоморфная плашка.
- **Единый фон + красная точка у выбранного.** Тёмную подложку рисует сам Flutter:
  выбранный пункт оборачивается в `Ink(color: Theme.of(context).focusColor)` и получает
  `autofocus`. Гасим `Theme` с `focusColor: Colors.transparent` — он доходит до пунктов, потому
  что `DropdownButton` захватывает окружение через `InheritedTheme.capture`. Отметка выбора —
  точка `AppSizes.kDotMark` цветом `AppColors.kDanger`; ставится и на «все», когда фильтр снят.

## 3. Привязка ШК из карточки товара

Клиентского метода привязки не было — на бэкенде `POST /barcodes` есть с P-FS-03.

- **`CatalogRepository.bindBarcode()`** — `POST /barcodes` (`good_id`/`barcode`/`symbology`).
  `symbology` шлём пустой: код мог прийти сканом или руками, символику не знаем — так же
  поступает поток ввода остатков. 409 приходит как `Failure.server(409)`.
- **`StockDetailCubit.bindBarcode()`** возвращает `Failure?`, а **не кладёт ошибку в state**:
  иначе карточка позади диалога ушла бы в экран ошибки. При успехе — `load()`, список ШК
  приходит с сервера, а не собирается локально.
- **`BindBarcodeButton`** — неоморфная кнопка «Привязать штрихкод +» во всю ширину.
- **`BarcodesSection`:** ШК нет → **одна кнопка вместо блока** (заголовок «Штрихкоды (0)» и пустой
  раскрывающийся список только занимали бы место); ШК есть → кнопка внутри раскрытой секции под
  списком. До загрузки карточки секции нет совсем.
- **`BindBarcodeDialog`** (образец — `DateQtyDialog`): одно поле, «Отмена» и «Привязать».

### Решения по диалогу (согласованы с заказчиком)

| Вопрос | Решение |
|---|---|
| Enter от сканера | **Сразу привязывает** — скан одним движением, без второго тапа |
| ШК занят другим товаром (409) | **Ошибка под полем, диалог остаётся открыт**, код в поле, фокус возвращён — можно сразу пересканировать |
| Кнопка «Привязать» | Активна только при непустом поле (после `trim`) и вне запроса |

### Клавиатура: почему не «показать и спрятать»

Первая версия копировала приём экрана входа — дать клавиатуре открыться и спрятать её следующим
кадром (`TextInput.hide` в post-frame). На эмуляторе незаметно, **на DT50 это видимое мелькание
клавиатуры снизу**.

Сделано иначе: поле стартует с **`keyboardType: TextInputType.none`** — IME не запрашивается
вовсе, прятать нечего, фокус и курсор на месте, скан идёт в поле.

**Ручной ввод — через пересоздание соединения с IME.** Первая попытка (сменить `keyboardType`
на `text` и позвать `TextInput.show`) на устройстве не открывала клавиатуру совсем: соединение
создаётся в момент получения фокуса и живёт с той конфигурацией, с которой создано, — поле
оставалось `none`, а `TextInput.show` для такого соединения ничего не делает. Поэтому по тапу
снимаем фокус и возвращаем его следующим кадром: связь пересоздаётся как обычное текстовое поле
и клавиатура открывается сама. Закрыто тестом: до тапа `setClientArgs.inputType` =
`TextInputType.none`, после — `TextInputType.text`, фокус на месте.

✅ **Проверено на DT50:** с `TextInputType.none` HID-сканер по-прежнему наполняет поле, клавиатура
при открытии диалога не мелькает и открывается по тапу. Откат, если поведение изменится на другой
модели ТСД, — вернуть `TextInputType.text` (вернётся прежнее мелькание).

Тот же приём стоит перенести на экран входа и поля скана во «Вводе остатков» — там мелькание
такое же. Отдельной задачей, в этой не трогали.

### Ширина диалога

По итогам теста на DT50: подпись «Привязать» ломалась на две строки. `AlertDialog` по умолчанию
отступает 40 dp по бокам — на 360 dp экране это съедает ширину. Добавлен
`AppInsets.dialogInset` (16 по бокам), содержимое тянется `SizedBox(width: double.maxFinite)`,
«Отмена» — по содержимому, весь остаток отдан «Привязать». Проверено измерением: высота подписи
20 px (одна строка) против 40 px до правки.

## 4. Расследование: лишний запрос при переходе в карточку

**Лишнего запроса нет.** При переходе уходят ровно два, оба по выбранному товару:
`GET /stock?good_id=…` и `GET /goods/{id}/barcodes`. Второй в логах выглядит как обращение
к `/goods/...`, что и вводило в заблуждение.

Замеченные в логе `GET /goods?q=фома+бекон` и `GET /goods?limit=50&offset=0` отработали **до**
перехода: первый — поиск, второй — очистка строки крестиком (список обязан что-то показать).
Порядок доказан идентификаторами товаров в последующих `/stock`: это первые две позиции
**полного** каталога, значит полный список уже был на экране в момент тапа.

Подтверждено виджет-тестом: `push` поверх экрана списка и `pop` обратно не дают ни одного
запроса — экран не пересоздаётся, повторный `init()` не запускается.

**Побочная находка (в код не вошла).** Отложенный поиск переживает уход с экрана: `openDetail`
и `openStockEntry` не отменяют дебаунс, а `push` экран списка не уничтожает. Тап по товару
в пределах 350 мс после последней буквы → запрос уходит из-под карточки, и при просадке связи
кладовщик возвращается **на экран ошибки** (`_load` при ошибке ставит `status: error`).
Критичность низкая, чинить ~20 мин. Занесено в `dev-context.md` §9 с оценкой.
