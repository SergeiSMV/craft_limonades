# Развёртывание: боевой сервер (prod)

Установка «в одну команду», обновления, бэкапы и восстановление на боевом сервере.
Локальная машина - в [dev-deploy.md](dev-deploy.md).

> ⚠ **Никогда на проде:** `migrate down` и `docker compose down -v` - сотрут данные.
> Схема двигается только вперёд.

---

## 0. Панель управления - единственное, что нужно запускать

На сервере всё делается через одно меню. Оно же ставит проект на чистой машине, оно же
обновляет, показывает состояние и работает с бэкапами на уже работающем сервере.

```bash
sudo bash /opt/craft-wms/app/deploy/craft.sh
```

В шапке - сводка состояния: домен, образ, какие контейнеры подняты, отвечает ли `/ready`,
когда снят последний дамп. Дальше пункты:

| Раздел                 | Пункты                                                                          |
|------------------------|---------------------------------------------------------------------------------|
| Установка и обновление | установить/переустановить · обновить сейчас · история обновлений                |
| Состояние              | **что готово, а что ещё нужно** · контейнеры и таймеры · логи · пробы           |
| Бэкапы                 | настроить (шифрование, где хранить) · список · снять · проверить · восстановить |
| Конфигурация           | показать `.env.prod` (секреты скрыты) · отредактировать                         |
| Мониторинг             | настроить (общий Bugsink, таймеры) · проверить                                  |
| Честный знак           | настроить подписант · проверить (подпись → токен → чтение марки)                |

Меню - обёртка над теми же скриптами, что описаны ниже; вручную их запускать по-прежнему
можно. Права поднимаются только там, где они нужны: установка и обновление идут через `sudo`
(apt и юниты systemd), а бэкап с восстановлением - нет, им достаточно доступа к docker.

**Пункт «Что готово, а что ещё нужно»** проходит всю цепочку - настройки без шаблонных
значений, DNS домена, docker, контейнеры, версия схемы и наличие пользователей, пробы
`/ready` и HTTPS снаружи, включённые таймеры, шифрование, внешняя копия, свежесть последнего
дампа - и по каждому «не готово» пишет, каким пунктом меню это закрывается. Это ответ
на вопрос «я всё настроил или нет».

**Пункт «Настроить бэкапы» проводит по шагам** - это то, что обычно
откладывают. Он генерирует парольную фразу и записывает её в `.env.prod`, показывает один раз
и требует набрать «СОХРАНИЛ» (фраза обязана существовать вне сервера, иначе внешняя копия
нечитаема), спрашивает, где хранить копии - на сервере, на Яндекс.Диске или и там, и там, - и в конце
снимает контрольный бэкап, показывая, что копия действительно доехала.

Для Яндекс.Диска нужен **пароль приложения**, а не пароль от аккаунта: доступ идёт
по протоколу WebDAV, и Яндекс выдаёт для него отдельный пароль. Создаётся он в браузере
на любом устройстве - телефон подойдёт, на сервере браузер не нужен:

1. Откройте <https://id.yandex.ru/security/app-passwords>
2. Выберите тип доступа **«Файлы» (WebDAV)**
3. Назовите пароль, например «craft-wms сервер», и создайте
4. Яндекс покажет пароль **один раз** - скопируйте его

Дальше мастер спросит логин и этот пароль, поставит `rclone`, если его нет, создаст папку
для дампов, покажет свободное место и **проверит подключение по-настоящему**: зальёт пробный
файл, убедится, что он виден в списке, и удалит его. Просто «пускают» - ещё не значит
«работает»: доступ может быть, а запись не проходить из-за квоты или прав. Раз бэкап нужен
для восстановления, проверяется именно то, от чего оно зависит.
Если Диск не пускает, мастер объяснит две обычные причины (введён пароль аккаунта вместо
пароля приложения; пароль скопирован не полностью) и **сотрёт введённые значения**: лучше явное
«не настроено», чем запись о копии, которой нет.

Пароль приложения даёт доступ только к файлам Диска и отзывается там же, не затрагивая
основной пароль аккаунта.

Логин и пароль хранятся в `.env.prod` рядом с остальными секретами; **файл конфигурации
`rclone` не нужен** - подключение собирается из этих значений при каждом вызове. Поэтому
не возникает вопроса, в чьём домашнем каталоге лежит конфигурация: бэкап по расписанию
запускает systemd от root, а меню без `sudo` перезапускается через него само.

**`.env.prod` - `root 600`** (ADHOC-44): в нём пароль базы, JWT-секрет, фраза шифрования
бэкапов, токен GHCR. Права выставляют `install.sh` и каждый прогон
`update.sh`; скрипт, запущенный без прав, отказывает с подсказкой «через sudo», а не работает
с пустыми значениями.

Выбор «только на сервере» тоже допустим, но мастер прямо скажет, чем это плохо: дампы окажутся
на том же диске, что и база, и отказ диска, кража или шифровальщик унесут всё разом.
Если фраза уже задана, мастер предупредит: смена делает **уже снятые дампы нечитаемыми**,
и без явного согласия ничего не тронет.

⚠ Пункт «восстановить из дампа» - разрушающий: он замещает базу. Меню сначала показывает
список дампов, потом спрашивает подтверждение, и лишь затем передаёт управление
`pg-restore.sh`, который спросит ещё раз, уже именем базы.

**На новом сервере** меню запускается до всякой установки: `.env.prod` ещё нет, и вместо
сводки выводится подсказка начать с пункта 1.

## 1. Откуда берётся образ (CI → GHCR)

CI (GitHub Actions) на **push в `dev`/`main`** собирает образ `apps/backend/Dockerfile` и публикует в
**GHCR**: `ghcr.io/<owner>/craft-wms-backend` с тегами `:<ветка>` и `:<sha>` (ADR-0009). Для прод-развёртывания
берётся образ, прошедший проверки, а не собранный вручную.

## 2. Установка на сервер

После установки приложение доступно по **HTTPS** и **само обновляется** при выходе новых версий.
Ставится «в одну команду». Обоснование топологии - ADR-0011.

### Что нужно от сервера (один раз)

- Linux (Debian/Ubuntu) с доступом `sudo`.
- **Домен**, A-запись которого указывает на внешний IP сервера.
- На роутере - **проброс портов 80 и 443** на сервер (нужно для HTTPS и выпуска сертификата).
- Прямой выход сервера в интернет.

Docker / nginx / certbot заранее ставить **не нужно** - `install.sh` сам доустановит, чего не хватает.

### Установка - 3 шага

**1. Создать рабочую папку и файл настроек `.env.prod`:**
```bash
sudo mkdir -p /opt/craft-wms && cd /opt/craft-wms
sudo nano .env.prod        # вставить содержимое infra/.env.prod.example и заполнить (см. ниже)
sudo chmod 600 .env.prod   # секреты: читает только root (то же сделает install.sh)
```

**2. Дать серверу доступ к приватному репозиторию - deploy key (read-only).**

По HTTPS не подойдёт: авто-обновление (`update.sh`) делает `git pull` из systemd-таймера, где нет
терминала, и запрос логина/токена там просто некому ввести. Нужен ключ, лежащий у root.

Сначала проверьте, нет ли ключа у root уже - генерация с тем же именем затрёт существующий,
и то, что им пользовалось, отвалится:
```bash
sudo ls -la /root/.ssh/
sudo ssh -o BatchMode=yes -o ConnectTimeout=5 -T git@github.com   # вдруг доступ уже есть
```
Если `Hi <репозиторий>! You've successfully authenticated` - ключ уже настроен, шаг можно пропустить.
Если приватного ключа (`id_ed25519`/`id_rsa`) нет - создать:
```bash
sudo ssh-keygen -t ed25519 -C "craft-wms deploy $(hostname)" -f /root/.ssh/id_ed25519 -N ""
sudo cat /root/.ssh/id_ed25519.pub          # ← скопировать
```
Если ключ есть, но занят под другое - завести отдельный (`-f /root/.ssh/id_craft_wms`) и указать
его для github.com в `/root/.ssh/config`.

Публичный ключ добавить в GitHub: репозиторий → **Settings → Deploy keys → Add deploy key**,
галку «Allow write access» **не ставить** - серверу нужно только читать.

Заранее доверить хост, иначе таймер упрётся в вопрос про fingerprint, на который никто не ответит:
```bash
sudo mkdir -p /root/.ssh && sudo ssh-keyscan github.com | sudo tee -a /root/.ssh/known_hosts >/dev/null
```

**3. Скачать код** (по SSH, не по HTTPS):
```bash
sudo git clone git@github.com:SergeiSMV/craft_limonades.git app
```

**4. Запустить панель управления и выбрать пункт 1 - установку** (ПО → nginx+TLS → запуск →
миграции → админ → авто-обновление):
```bash
sudo bash app/deploy/craft.sh
```

То же самое напрямую, если меню не нужно: `sudo bash app/deploy/install.sh`.

Готово. Проверка: открыть в браузере **`https://<ваш-домен>/health`** - должно вернуть `200`,
либо пункт 6 в меню.

### Что заполнить в `.env.prod`

Замените все значения с `CHANGE_ME`. Минимум:
- `DEPLOY_DOMAIN` - ваш домен;
- `CERTBOT_EMAIL` - ваш e-mail (для уведомлений Let's Encrypt);
- `POSTGRES_PASSWORD`, `JWT_SECRET` - секреты;
- `ADMIN_PASSWORD` - пароль администратора.

> ⚠️ Комментарии в `.env.prod` - **только на отдельной строке**, не рядом со значением.

Сгенерировать секреты одной строкой:
```bash
echo "JWT_SECRET=$(openssl rand -base64 48)"
echo "POSTGRES_PASSWORD=$(openssl rand -base64 24 | tr -dc A-Za-z0-9 | head -c 32)"
```

### Доступ к образу: сделать GHCR-пакет публичным (рекомендуется)

Проще всего один раз сделать docker-образ публичным - тогда серверу **не нужен токен**:
GitHub → аватар → **Packages** → `craft-wms-backend` → **Package settings** → **Change visibility** → **Public**.

Если образ остаётся приватным - заполните `GHCR_USER` и `GHCR_TOKEN` (PAT со scope `read:packages`) в `.env.prod`.

### Обновления - автоматически

При `AUTO_UPDATE=true` сервер обновляется сам каждые `UPDATE_INTERVAL` (по умолчанию 5 минут).
Путь релиза на прод: смержили **`dev → main`** → CI собрал образ `:main` → сервер подтянул.
Делать ничего не нужно.

Обновляется **всё**, а не только образ:

1. `git pull` в `/opt/craft-wms/app` - скрипты деплоя и systemd-юниты;
2. переустановка юнитов из репозитория (идемпотентно);
3. образ backend из GHCR; если в нём есть новые миграции - **дамп базы**, затем миграции;
4. проверка `/ready` - если не отвечает, в journal уходит запись с приоритетом error.

```bash
systemctl list-timers 'craft-wms-*'         # когда следующая проверка
journalctl -u craft-wms-update -n 30        # что делало авто-обновление
sudo bash /opt/craft-wms/app/deploy/update.sh   # обновить прямо сейчас, вручную
```

**Одна команда обновляет сервер целиком** - отдельно тянуть репозиторий и переставлять юниты не нужно.

Две особенности, о которых стоит знать:

- **`update.sh` перезапускает сам себя из временной копии** перед `git pull`. Иначе новая версия
  подменила бы файл на ходу: bash дочитывает скрипт с диска по мере выполнения, и получилась бы
  смесь старой и новой версии. Побочное следствие: правки в самом `update.sh` вступают в силу
  со **следующего** запуска.
- **`SELF_UPDATE=false`** в `.env.prod` отключает шаги 1-2: код деплоя тогда обновляется только
  вручную (`git pull` + `install.sh`), а таймер продолжает обновлять образ.
- **Перед миграциями снимается дамп базы** - только когда есть что применять (`migrate pending`
  свежего образа), иначе таймер снимал бы его каждые 5 минут. Дамп ложится в
  `/opt/craft-wms/premigrate/` (`PREMIGRATE_DIR`), хранятся последние 5 (`PREMIGRATE_KEEP`). Он
  не шифруется и наружу не уходит - на сервере открытым лежит и ночной дамп; ночная ротация и
  внешняя копия этот каталог не трогают. **Не снялся дамп - обновление останавливается до
  миграций**, работает прежняя версия, в journal - запись с приоритетом error. Не удалось
  узнать, есть ли новые миграции, - дамп снимается на всякий случай.

### Бэкапы БД и восстановление

**По расписанию - ничего делать не нужно.** `install.sh` ставит два systemd-таймера (при
`AUTO_BACKUP≠false` в `.env.prod`):

| Таймер                    | Когда           |
|---------------------------|-----------------|
| `craft-wms-backup`        | ежедневно 03:30 |
| `craft-wms-restore-check` | вс 04:30        |

`craft-wms-backup` делает `pg_dump` → gzip в `/opt/craft-wms/backups` → шифрование паролем →
отправку во внешнюю копию, затем ротацию по `KEEP_DAYS` (14 дней).
`craft-wms-restore-check` разворачивает последний дамп во временную базу, сверяет состав
и удаляет её.

Расписание - `BACKUP_SCHEDULE` / `RESTORE_CHECK_SCHEDULE` в `.env.prod`, формат
[systemd OnCalendar](https://www.freedesktop.org/software/systemd/man/systemd.time.html).
У обоих `Persistent=true`: если сервер был выключен в назначенный час, задание отработает
сразу после включения - сервер тут ноутбук, его выключают.

Проверка восстановимости не трогает ни прод-базу, ни backend: дамп разворачивается в отдельную
базу `craft_wms_restore_check`, которая удаляется в конце (в том числе при ошибке). Смысл - ловить
битые дампы заранее: бэкап, который ни разу не разворачивали, это файл неизвестного качества.

```bash
systemctl list-timers 'craft-wms-*'              # когда следующий запуск
journalctl -u craft-wms-backup -n 30             # что делал бэкап
journalctl -u craft-wms-restore-check -n 30      # результат последней проверки

bash /opt/craft-wms/app/deploy/pg-backup.sh              # разовый дамп прямо сейчас
bash /opt/craft-wms/app/deploy/pg-restore.sh --check     # проверить последний дамп вручную
```

#### Веб-портал

Бандл портала приезжает **образом из GHCR** и раскладывается в `PORTAL_ROOT`, откуда его
отдаёт хостовый nginx. Публикацию делает CI при мерже в `main`; сервер забирает образ
в обычном обновлении, отдельного пункта для этого не нужно - но он есть на случай, когда
надо обновить только вёрстку: «Обновить веб-портал».

```
PORTAL_IMAGE=ghcr.io/sergeismv/craft-wms-portal:main
```

Бандл собран с относительным адресом API (`/api/v1/`), поэтому не привязан к домену: портал
и API живут на одном origin (ADR-0015), и один и тот же образ годится для любого сервера.

Подмена атомарная: файлы извлекаются во временный каталог, проверяется наличие `index.html`,
и только потом каталог подменяется. Так nginx не отдаст наполовину скопированный бандл.
Неудача обновления портала не роняет обновление сервера - прежний бандл остаётся на месте,
а в journal уходит ошибка.

⚠ **Пакет `craft-wms-portal` должен быть публичным.** Первая публикация создаёт его приватным
по видимости репозитория; переключается один раз в настройках пакета на GitHub. Публичные
пакеты в GHCR не тарифицируются, а бандл весит около 50 МБ. Раскрытия при этом нет: портал
и так отдаётся браузеру любого посетителя. Репозиторий при этом остаётся приватным -
видимость пакета задаётся отдельно.

#### Шифрование дампов

В дампе - ФИО сотрудников, логины и хеши паролей, плюс вся товарная база. Наружу такой файл
должен уезжать только шифрованным, поэтому **без пароля внешняя копия не отправляется вовсе**
(в journal пишется ошибка): выносить незашифрованное хуже, чем не выносить.

Настройка - одна строка в `.env.prod`:

```bash
openssl rand -base64 32        # сгенерировать фразу
```
```
BACKUP_PASSPHRASE=сюда-сгенерированную-фразу
```

Больше ничего не нужно: шифрует `openssl` (предустановлен), ключ выводится PBKDF2 с 600000
итераций, пароль передаётся процессу через окружение - в списке процессов он не виден.

> ⚠ **Запишите фразу вне сервера** - строкой в менеджере паролей, рядом с остальными секретами
> проекта. `.env.prod` живёт только на сервере: если он погибнет вместе с диском, внешняя копия
> останется нечитаемой, то есть внешней копии фактически нет. Это единственное, что требуется
> помнить, - но это требуется.
>
> ⚠ **Смена фразы обрывает доступ к уже снятым дампам:** они зашифрованы старой. Меняя её,
> сначала расшифруйте то, что хотите сохранить.

Файлов-ключей здесь намеренно нет. Их пришлось бы где-то хранить и не потерять, а потерянный
ключ убивает бэкапы так же надёжно, как их отсутствие. Заодно это исключает `age -p`: он читает
парольную фразу только с терминала и в systemd-таймере падает с
`standard input is not a terminal`.

Незашифрованный `.sql.gz` **остаётся на сервере** до ближайшей ротации - на нём работает
еженедельная проверка восстановимости, которой иначе пришлось бы каждый раз расшифровывать.
Наружу уезжает только `.enc`.

#### Внешняя копия дампов

Дампы на том же диске, что и база, не спасают от того, ради чего бэкап и заводят: отказ диска,
кража ноутбука, шифровальщик уносят и базу, и дампы разом. Настраивается двумя независимыми
переменными - можно задать обе, тогда копия уедет в два места.

**rsync - внешний диск или второй хост в LAN.** Одна переменная, две формы; rsync их не различает.

```
OFFSITE_DEST=/mnt/craft-backup                       # смонтированный внешний диск
OFFSITE_DEST=backup@192.168.0.50:/srv/craft-wms      # второй хост в LAN
OFFSITE_SSH_KEY=/root/.ssh/id_craft_backup           # только для формы user@host
```
Каталог назначения должен быть **выделен под дампы**: внутри работает зеркалирование ротации
(`--delete` по нашему шаблону имён). Чужие файлы в этом каталоге не удаляются, но и путаться
с ними незачем. Для локального пути скрипт проверяет, что каталог существует, и предупреждает,
если это не точка монтирования: отвалившийся внешний диск оставляет пустой каталог, и без
проверки rsync бодро отработал бы «в никуда».

**rclone - облако, в том числе Яндекс.Диск.** Протокола Яндекс.Диска rsync не знает, поэтому
единственный путь туда - `rclone` (у него нативный бэкенд `yandex`).

```bash
curl https://rclone.org/install.sh | sudo bash    # из apt ставить не стоит: там старые версии
rclone config                                     # n → имя remote → тип yandex → OAuth в браузере
rclone lsd yandex:                                # проверка, что remote отвечает
```
```
OFFSITE_RCLONE_REMOTE=yandex:craft-wms-backups
```
Ротация в облаке - `rclone delete --min-age ${KEEP_DAYS}d`, иначе дампы копились бы там вечно.

⚠ Вынос данных за пределы склада - **решение заказчика**: в дампе персональные данные
сотрудников. Яндекс.Диск в этом смысле удобнее зарубежных облаков (серверы в РФ), но спросить
всё равно нужно.

Проверить, что копия реально уезжает:
```bash
bash /opt/craft-wms/app/deploy/pg-backup.sh      # в выводе - строка «Внешняя копия обновлена»
ls -l /mnt/craft-backup                          # или: rclone ls yandex:craft-wms-backups
```

#### Восстановление после потери данных

⚠ **Разрушающая операция:** содержимое базы замещается дампом.

```bash
bash /opt/craft-wms/app/deploy/pg-restore.sh                     # из самого свежего дампа
bash /opt/craft-wms/app/deploy/pg-restore.sh /path/to/dump.gz    # из конкретного
bash /opt/craft-wms/app/deploy/pg-restore.sh /path/to/dump.enc   # из зашифрованного
```

Если данные испортила миграция при обновлении, ближайшая точка - дамп перед миграциями:
`pg-restore.sh /opt/craft-wms/premigrate/craft_wms-premigrate-<время>.sql.gz`. Схема в нём -
прежняя, а таймер обновления через 5 минут накатит ту же миграцию снова - поэтому сначала
`sudo systemctl stop craft-wms-update.timer`, затем восстановление, и таймер включается обратно
только с исправленной миграцией в `:main`.

Зашифрованный `.enc` скрипт распознаёт сам (и выбирает его при авто-подборе, если незашифрованных
дампов уже не осталось): расшифровывает во временный файл с правами `600`, который удаляется при
любом исходе. Пароль берётся из `BACKUP_PASSPHRASE`; если он не тот, скрипт отказывается до того,
как что-либо тронет. Расшифровать вручную, вне сервера:

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -pass env:PASS \
  -in craft_wms-20260902-033000.sql.gz.enc -out dump.sql.gz
```

Что делает скрипт, по шагам: проверяет целостность архива → **снимает страховочный дамп текущего
состояния** (`pre-restore-*.sql.gz`, остаётся в `backups/`) → останавливает backend и рвёт
оставшиеся соединения → пересоздаёт базу → разворачивает дамп → сверяет состав → поднимает backend.

Подтверждение - ввод имени базы (`craft_wms`); любой другой ответ прерывает без изменений.
Ключ `--yes` пропускает вопрос (для скриптов). Ошибка на любом шаге прекращает работу: битый архив
отсекается **до** остановки backend, пустой страховочный дамп - **до** удаления базы.

После восстановления проверьте `https://<домен>/ready` (200).

### Мониторинг: ошибки, доступность, таймеры

Три вопроса - три инструмента:

| Инструмент      | Отвечает на вопрос                     | Где живёт                  |
|-----------------|----------------------------------------|----------------------------|
| UptimeRobot     | доступен ли сервер снаружи             | внешний сервис             |
| Cronitor        | отработали ли таймеры по расписанию    | внешний сервис             |
| Bugsink         | какие ошибки случаются внутри работы   | на сервере, `/opt/bugsink` |

Всё выключено, пока в `.env.prod` пусто: стек работает как без мониторинга.

#### UptimeRobot - доступность снаружи

HTTP-монитор `https://<DEPLOY_DOMAIN>/ready` раз в 5 минут, письма на почту учётной записи.
`/ready` отвечает 200, только если бэкенд жив и достаёт до базы, поэтому монитор ловит и
выключенный сервер, и пропавший интернет, и упавший nginx или бэкенд. Настраивается в
интерфейсе сервиса, в коде не участвует.

#### Cronitor (или Healthchecks.io) - таймеры

Три монитора типа «heartbeat / job», у каждого свой адрес:

| Монитор         | Период   | Запас  | Переменная в `.env.prod`  |
|-----------------|----------|--------|---------------------------|
| update          | 5 минут  | 15 мин | `JOB_PING_UPDATE`         |
| backup          | 1 день   | 2 ч    | `JOB_PING_BACKUP`         |
| restore-check   | 7 дней   | 6 ч    | `JOB_PING_RESTORE_CHECK`  |

Адрес Cronitor - `https://cronitor.link/p/<ключ>/<монитор>`, Healthchecks.io -
`https://hc-ping.com/<uuid>`; формат сигнала скрипт выбирает по адресу. По окончании скрипт
сообщает исход: успех или сбой с кодом и текстом последней ошибки. Не пришёл к сроку или
пришёл сбой - письмо. Сигнал `update` заодно значит «сервер на месте», а `update.sh` перед
ним проверяет `/ready` через хостовый nginx и TLS: упавший nginx или истёкший сертификат дают
сбой.

#### Bugsink - ошибки бэкенда, ТСД и портала

Свой сервер сбора ошибок, совместимый с Sentry, - **общий для всех проектов сервера**:
отдельный стек `/opt/bugsink` (Bugsink и его Postgres, секреты в `/opt/bugsink/.env`, только
для root), интерфейс - `https://errors.skogi.ru`. В стеке Craft его нет (ADHOC-73): остановка
или удаление стека Craft приём ошибок других проектов не трогает. Ставит и подключает его
общий скрипт `deploy/bugsink.sh`; у каждого проекта своя команда, у Craft - `craft` с проектами
`craft-backend` (сервер) и `craft-app` (ТСД и портал, их события идут через бэкенд).
Бэкенд шлёт туда каждую запись журнала уровня error и каждую панику запроса - с запросом
(без токена), `request_id` и пользователем. База Bugsink не бэкапится.

Включение - **панель управления, пункт 16 «Настроить мониторинг»**
(`sudo bash /opt/craft-wms/app/deploy/craft.sh`), или напрямую:

```bash
sudo bash /opt/craft-wms/app/deploy/monitoring-setup.sh
```

Скрипт спрашивает адреса трёх мониторов таймеров (Enter - оставить как есть), остальное делает сам:

1. `deploy/bugsink.sh`: Bugsink на сервере есть - подключается к нему; нет - ставит в
   `/opt/bugsink` (спрашивает домен, почту и пароль администратора, Enter - сгенерировать;
   vhost и сертификат Let's Encrypt; нужна DNS-запись домена на сервер);
2. заводит команду `craft` и проекты, включает письма о новых ошибках, пишет DSN в
   `SENTRY_DSN` и `CLIENT_SENTRY_DSN` (`https://<ключ>@errors.skogi.ru/<номер>`);
3. `SENTRY_HOST` - хост Bugsink: в compose он указывает на сам сервер (`host-gateway`), события
   идут в хостовый nginx этой же машины, наружу не выходят;
4. пересоздаёт backend с новым окружением;
5. проверка: проверочная ошибка из backend - скрипт ждёт, пока она появится в Bugsink.

В конце `bugsink.sh` печатает адрес, логин и пароль администратора - пароль он проверяет в
Bugsink и, если тот не подходит (меняли в интерфейсе), предлагает задать новый. Повторный
запуск безопасен: команда и проекты не задваиваются, DSN не меняются.

Письма об ошибках (SMTP-ящик, **пароль приложения**) - в `/opt/bugsink/.env`, переменные
`BUGSINK_EMAIL_*` (порт 465 - `USE_SSL=True`, `USE_TLS=False`; 587 - наоборот), затем:

```bash
sudo docker compose --env-file /opt/bugsink/.env -f /opt/bugsink/docker-compose.yml up -d
```

Проверить мониторинг в любой момент - пункт 17 «Проверить мониторинг» или:

```bash
sudo bash /opt/craft-wms/app/deploy/monitoring-setup.sh --test
```

Проверочная ошибка - запрос админа `POST /api/v1/admin/monitoring/test`: пишет в журнал ошибку
«проверка мониторинга» и проходит весь путь до Bugsink. Письмо о новой ошибке Bugsink шлёт один
раз на ошибку: чтобы проверить письмо снова, отметьте её в интерфейсе решённой (Resolve).

### Честный знак: подписант (CZ-02)

WMS читает данные марок через True API Честного знака. Токен True API выдаётся в обмен на
строку, подписанную КЭП сотрудника с МЧД. Подписывает **служба на хосте**
`craft-wms-cz-signer`, а не контейнер: КриптоПро CSP, ключ и лицензия стоят на сервере.
Бэкенд ходит к ней через unix-сокет `/run/cz-signer/sign.sock` - каталог смонтирован в его
контейнер, доступ даёт группа `cz-signer`. В сеть подписант не выходит, ключ в бэкапы не
попадает.

Нужно заранее, руками (один раз):

- КриптоПро CSP 5 для Linux на сервере;
- файловая копия ключа подписанта в `/var/opt/cprocsp/keys/<пользователь>` со своим паролем;
- сертификат подписанта в личном хранилище `uMy` этого пользователя, привязанный к копии.

Дальше - **панель, пункт 18 «Настроить подписант»**, или напрямую:

```bash
sudo bash /opt/craft-wms/app/deploy/cz-setup.sh
```

Скрипт спрашивает пользователя с ключом, показывает его сертификаты, спрашивает отпечаток и
пароль копии (Enter - оставить как есть), затем:

1. пишет отпечаток и пароль в `/opt/craft-wms/cz-signer.env` (root, `600`) - не в
   `.env.prod`: пароль ключа не нужен ни бэкенду, ни остальным скриптам;
2. пишет в `.env.prod` `CZ_SIGNER_USER` и `CZ_SIGNER_SOCKET`, заводит группу `cz-signer` и
   записывает её номер в `CZ_SIGNER_GID`;
3. ставит юнит и бинарь `/opt/craft-wms/bin/cz-signer` (он едет в образе бэкенда),
   перезапускает службу;
4. пересоздаёт backend с сокетом и проверяет всё по звеньям.

Проверить в любой момент - пункт 19 «Проверить ЧЗ» или:

```bash
sudo bash /opt/craft-wms/app/deploy/cz-setup.sh --test
```

Проверка идёт по звеньям, чтобы сразу было видно, где сломалось:

1. служба работает;
2. пробная подпись прямо через сокет;
3. бэкенд получил токен (`GET /api/v1/admin/cz/status`);
4. по желанию - чтение марки по введённому КИ (`POST /api/v1/admin/cz/info`).

Дальше всё само: `update.sh` достаёт из каждого нового образа бэкенда свежий бинарь
подписанта и перезапускает службу, бэкенд обновляет токен за час до истечения. Сбой входа в
True API бэкенд пишет в журнал ошибкой - она приходит письмом из Bugsink.

⚠ **Лицензия КриптоПро CSP на сервере пробная** - до ~2027-01-24. Истечёт - подписант
перестанет подписывать, и чтение марок встанет. Срок показывает пункт 5 «Что готово».
Постоянную лицензию купить заранее.

### Где смотреть, если что-то не так

| Что                          | Где                                                                  |
|------------------------------|----------------------------------------------------------------------|
| Ошибки бэкенда с разбором    | Bugsink - `https://errors.skogi.ru`                                  |
| Журнал бэкенда целиком       | панель, пункт 7 «Логи backend»                                       |
| Автообновление               | `journalctl -u craft-wms-update -n 50`                               |
| Бэкап и его проверка         | `journalctl -u craft-wms-backup`, `journalctl -u craft-wms-restore-check` |
| Bugsink сам                  | `docker logs bugsink-bugsink-1` (стек `/opt/bugsink`)                |
| Подписант Честного знака     | `journalctl -u craft-wms-cz-signer -n 50`                            |
| nginx: вход снаружи, TLS     | `/var/log/nginx/access.log`, `/var/log/nginx/error.log`              |
| Доступен ли сервер снаружи   | UptimeRobot                                                          |
| Отработали ли таймеры        | Cronitor                                                             |

`docker compose …` - полностью:
`sudo docker compose --env-file /opt/craft-wms/.env.prod -f /opt/craft-wms/app/infra/docker-compose.prod.yml`
(`sudo` - файл настроек читает только root).

**Автообновление завершается ошибкой, если не скачался образ backend или портала** - работа
при этом сделана, стек живёт на прежних образах. Частая причина - истёк `GHCR_TOKEN`
(personal access token GitHub с правом `read:packages`): так прод 20-23.10.2026 трое суток
стоял на сборке 13 октября, а скрипт отчитывался «Обновление завершено». Новый токен -
GitHub → Settings → Developer settings → Personal access tokens, в `.env.prod` заменить
`GHCR_TOKEN=`; таймер подхватит его в течение 5 минут.

### Файрвол (по желанию)

`install.sh` файрвол **не трогает** (сервер может обслуживать и другие сайты). Если нужен:
```bash
sudo ufw allow 22,80,443/tcp && sudo ufw enable
```

### Если что-то не так

- **`/health` не отвечает** - логи backend:
  `docker compose --env-file /opt/craft-wms/.env.prod -f /opt/craft-wms/app/infra/docker-compose.prod.yml logs backend`
- **Сертификат не выпустился** - проверьте, что домен резолвится и порт 80 проброшен: `dig +short <домен>`.
- **Никогда на проде:** `migrate down` и `docker compose down -v` - сотрут данные. Схема двигается только вперёд.
