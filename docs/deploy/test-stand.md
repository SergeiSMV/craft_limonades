# Тестовый стенд: копия боевого контура на машине разработчика

Стенд — Postgres со снимком боевой базы, бэкенд **текущей ветки** и портал за nginx, в той же
раскладке, что на проде (API под `/api/v1/`, пробы на корне, портал на `/`). На нём новые
миграции и код проверяются на настоящих данных до мержа: миграция, упавшая на живых данных,
падает здесь, а не на сервере.

Стенд живёт отдельным compose-проектом `craft-stand` со своими портами и своей базой и не
задевает обычный dev-стек (`make up`). В боевую базу стенд не пишет никогда: подключения к ней
у него нет, снимок приходит файлом.

Всё управление — одним скриптом: `bash deploy/test_stand/stand.sh <команда>`.

## Как устроено

```
боевой сервер                          эта машина
craft-wms-db-1 ── pg_dump -Fc ──SSH──▶ deploy/test_stand/snapshots/prod-<время>.dump
                                                  │ pg_restore
                                                  ▼
                                       craft-stand-db-1 (127.0.0.1:5433)
                                                  │ migrate up (миграции ветки)
                                                  ▼
                       craft-stand-backend-1 (сборка ветки) ◀── nginx :8090 ◀── портал, ТСД
```

| Файл                                         | Что                                          |
|----------------------------------------------|----------------------------------------------|
| `deploy/test_stand/stand.sh`                 | управление стендом                           |
| `deploy/test_stand/docker-compose.stand.yml` | db, backend (сборка ветки), nginx            |
| `deploy/test_stand/nginx.stand.conf`         | раскладка как у боевого vhost                |
| `deploy/test_stand/stand.env.example`        | шаблон настроек                              |
| `deploy/test_stand/stand.env`                | настройки стенда, создаётся сам, вне git     |
| `deploy/test_stand/snapshots/`               | снимки боевой базы, вне git, права 600       |

В снимке ФИО, логины и хеши паролей, поэтому снимки и настройки — в `.gitignore`, а файлы
снимков доступны только владельцу.

## Предусловия

- Docker через Colima. Если она остановлена, `stand.sh` запускает её сам.
- SSH-ключ этой машины принят боевым сервером без пароля, а пользователь на сервере — в группе
  `docker`. SSH на сервер пускает только из LAN: свежий снимок снимается, когда машина в одной
  сети с сервером. Вне LAN стенд работает на уже снятых снимках.
- Для портала и APK — Flutter (как для обычной сборки).

## Команды

| Команда                 | Что делает                                                        |
|-------------------------|--------------------------------------------------------------------|
| `stand.sh pull`         | снять свежий снимок боевой базы; стенд не трогает                  |
| `stand.sh up`           | поднять стенд: нет базы — из последнего снимка; есть — с ней       |
| `stand.sh reset [файл]` | вернуть базу к снимку (по умолчанию последнему) + миграции ветки   |
| `stand.sh refresh`      | `pull` + `reset`: свежий снимок и стенд на нём                     |
| `stand.sh migrate`      | пересобрать бэкенд ветки и накатить её миграции                    |
| `stand.sh portal`       | собрать портал; открывается на `http://localhost:8090`             |
| `stand.sh apk`          | собрать релизную APK для ТСД против стенда                         |
| `stand.sh status`       | контейнеры, адреса, свежий снимок                                  |
| `stand.sh snapshots`    | список снимков                                                     |
| `stand.sh logs [сервис]`| логи `backend`, `db`, `nginx`                                      |
| `stand.sh psql`         | консоль базы стенда                                                |
| `stand.sh down`         | остановить, база сохраняется                                       |
| `stand.sh destroy`      | удалить всё: стенд, базу, образ и снимки (с подтверждением)        |

База стенда помечена именем снимка, из которого развёрнута (`status` показывает его в строке
«База стенда»). `up` без метки считает базу неразвёрнутой и разворачивает последний снимок
заново — прерванное восстановление не оставит стенд на пустой базе.

Снимков хранится `STAND_KEEP_SNAPSHOTS` (по умолчанию 5), старые удаляются при `pull`.

`destroy` удаляет и снимки: в них боевые данные, а новый снимается за секунды. Ключи:
`--keep-snapshots` — оставить снимки (воспроизвести падение миграции на тех же данных или
поднять стенд вне LAN, где свежий снимок не снять), `--yes` — без подтверждения. Настройки
`stand.env` остаются: данных прода в них нет.

## Рабочий цикл

1. Поднять Docker и стенд со свежими данными:

   ```
   colima start
   bash deploy/test_stand/stand.sh refresh
   bash deploy/test_stand/stand.sh portal
   ```

   Ожидаемо: `migrate up: ok`, все три контейнера `healthy`, в конце адреса стенда.
   Вместо `refresh` — `up`, если нужен прежний снимок или база после прошлых тестов.

2. Проверить, что стенд живой:

   ```
   curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8090/ready
   bash deploy/test_stand/stand.sh psql -c 'select version, dirty from schema_migrations'
   ```

   Ожидаемо: `200`; версия схемы — последняя миграция ветки, `dirty = f`.

3. Работать: портал — `http://localhost:8090`, вход теми же учётными данными, что на проде
   (база — копия боевой). Токены прода стенд не принимает — у него свой JWT-секрет, вход заново.

4. Правка кода или новая миграция в ветке — пересобрать и накатить:

   ```
   bash deploy/test_stand/stand.sh migrate
   bash deploy/test_stand/stand.sh up
   ```

   Повторить проверку миграции с чистого листа — `stand.sh reset`: база возвращается к снимку
   без похода на сервер, миграции ветки накатываются заново.

5. Закончить — на время, с сохранением базы:

   ```
   bash deploy/test_stand/stand.sh down
   colima stop
   ```

   Или насовсем, не оставляя ничего (контейнеры, база, образ бэкенда, снимки):

   ```
   bash deploy/test_stand/stand.sh destroy
   colima stop
   ```

   Кэш сборки Docker общий с dev-стеком, `destroy` его не трогает; почистить —
   `docker builder prune -f`.

## ТСД на стенде

`stand.sh apk` собирает релизную APK с адресом этой машины в LAN
(`http://<IP>:8090/api/v1/`). Ставится вручную, как обычная (`adb install -r …`).

⚠ **Приложение стенда и боевое — одно и то же приложение** (тот же идентификатор), и очередь
операций на терминале переживает переустановку. Неотправленная операция, сделанная против
стенда, после установки боевой APK уйдёт на прод, и наоборот. Поэтому:

- переключать терминал между продом и стендом **только с пустой очередью** (экран
  «Несинхронизированное» пуст) — или удалять приложение перед установкой (`adb uninstall
  com.craftlimonades.sklad`), что стирает его данные;
- для стенда удобнее держать отдельный терминал.

## Чего стенд не повторяет

- **TLS и домен.** Стенд — по HTTP на порту 8090.
- **Образ бэкенда** собирается из рабочего дерева ветки, а не тянется из GHCR.
- **Таймеры** обновления, бэкапа и проверки восстановления на стенде не работают.
- **Данные** — на момент снимка: всё, что произошло на проде после `pull`, стенд не видит.
